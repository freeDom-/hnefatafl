# 0.28.0 - D4 symmetry augmentation of training samples

Phase 3: optional D4 symmetry augmentation of neural training samples. This is a
stable feature release with an annotated, unprefixed `0.28.0` tag. The previous
stable milestone `0.27.0` is already tagged and published; nothing was overwritten
or moved.

## Delivered behavior

- New validated training parameter `training_symmetry_mode`, `"off"` (default) or
  `"random_d4"`. Off preserves the existing baseline exactly, draws no extra random
  values and reproduces earlier CPU results bit-for-bit.
- `random_d4` draws one independent, uniform transform from the eight D4 elements
  (identity included) for every replay example presented to the optimizer, and
  redraws it on each later exposure. Minibatch size, epochs, optimizer steps, games,
  replay capacity and replay contents are unchanged.
- New pure module `hnefatafl/training_augmentation.py` transforms the six input
  planes, every policy action id and the legal mask with one cached `[8, n²]` square
  permutation and one `[8, n⁴]` action permutation per board size, keeps each MCTS
  probability paired with its transformed move, and leaves the defender-relative
  value untouched. The throne and corner planes are D4-invariant. Work happens on
  host tensors before the single device transfer, so no device kernels or copies are
  added and replay rows are never mutated.
- The optimizer loop was extracted into `optimize_replay`, shared by training and
  the new benchmark, so measured cost is the real cost.
- Augmentation uses a dedicated random stream (`augmentation_rng`) saved in full
  checkpoints. Resumed `random_d4` CPU runs reproduce uninterrupted runs exactly;
  legacy or `off` checkpoints resume as `off` unless explicitly changed, in which
  case a deterministic derivation from the unchanged seed and completed iteration is
  used. Source checkpoints are never rewritten and no format version changed.
- New metrics separate original replay positions from augmented training exposures:
  mode, training exposures, augmented exposures, identity count, eight per-transform
  counts, augmentation seconds and its share of optimization time.
- The workshop exposes **Training symmetry augmentation** (German:
  *Symmetrie-Datenaugmentation*) for new and resumed jobs, with a short explanation
  that this affects training samples rather than rules or search budgets. It is
  preserved by job/model parameter reuse, plans and JSON export, and shown in the
  performance panel.
- Remote workers advertise `training_symmetry_modes`; `random_d4` jobs only run on
  workers that support them, and the key is omitted from legacy worker transports.

## Scope boundaries

Augmentation changes training samples only. Self-play, MCTS, evaluation and the
Phase 1 exact-input cache and Phase 2 node-level prediction reuse are unchanged;
predictions for rotated or reflected positions are never merged or shared, because
training encourages but does not guarantee equivariance. No game rule, network
architecture, replay semantics or remote protocol beyond the new setting changed.

## Evidence

Full tables, environment and raw JSON: [symmetry-phase3.md](../benchmarks/symmetry-phase3.md);
metric definitions: [PERFORMANCE.md](../PERFORMANCE.md#phase-3-training-symmetry-augmentation).

- Augmentation work measured 1.4–1.9% of optimization time. End-to-end optimizer-time
  ratios (random_d4/off) had medians of 0.97–1.04 (CPU), 0.94–1.05 (CUDA FP32) and
  1.03–1.14 (CUDA mixed precision, RTX 3060) with ±20% per-repetition scatter; the
  CPU timings shared the host with an unrelated training job. Memory was unchanged.
- Mean policy total-variation distance between a position and its mapped-back
  rotations fell from 0.54/0.47/0.42 to 0.12/0.09/0.07 for Brandubh/Tablut/Copenhagen,
  and held-out policy loss fell in 9/9 replicates, while top-move agreement stayed far
  from exact.
- A 32-game paired smoke match per ruleset produced no distinguishable strength
  difference in either direction; Copenhagen was mostly unfinished. **No strength
  claim is made.** CUDA FP32 and mixed-precision training and resume were executed on
  an RTX 3060; MPS and OpenVINO GPU were not exercised for this feature.

## Validation

All commands below ran on the idle validation host (Linux/WSL2, 12 logical CPUs,
PyTorch 2.14.1 CPU wheel) unless a device is named.

- `make check` passed: documentation links/anchors (62 files, 385 links), Ruff
  lint/format, Prettier, mypy (33 files), TypeScript, **1,150 backend tests passed
  with 36 hardware skips**, **197 frontend unit tests passed** and the production
  Vite build.
- `npm --prefix frontend run test:e2e` passed **62 desktop/mobile Chromium checks
  with 4 intentional skips**, including the new `symmetry-augmentation.spec.ts`,
  which trains a real `random_d4` job through the API, asserts augmentation metrics
  and unchanged game counts, reuses the job's parameters in the workshop, checks the
  English and German control labels, and performs a reviewed resume that records the
  effective mode while leaving the source job untouched.
- New backend tests cover all eight transforms on all three rulesets (tensor versus
  transformed-state encoding, action-permutation inverses, legal-mask equality,
  probability pairing, king escape/capture, restricted squares, Copenhagen shield
  walls, non-mutation of replay rows), configuration validation, real optimizer
  updates and weight changes, same-seed reproducibility, different-seed divergence,
  uninterrupted-versus-resumed equality, legacy checkpoint loading, explicit
  off→random_d4 resumption without source rewrites, and remote-worker gating.
- Real training, checkpointing and resume were executed on CPU and on an NVIDIA
  RTX 3060 in both FP32 and mixed precision (including a resumed `random_d4` run).
- Browser checks required local Chromium libraries that are not installed
  system-wide here; they were supplied via `LD_LIBRARY_PATH` from extracted Ubuntu
  packages. This affects only the validation environment, not the application.

## Upgrade notes

No storage or checkpoint migration is required. Existing jobs and models keep
`off`. Update remote workers to 0.28.0 to run `random_d4` jobs remotely; older
workers continue to run `off` jobs. `random_d4` is **not** enabled by default; the
suggested experiment to decide that is in
[PERFORMANCE.md](../PERFORMANCE.md#recommended-experiment).

## Limitations

The evidence uses small networks, short budgets and single-seed throughput runs; it
demonstrates mechanism, cost and regularisation behavior, not production-scale
learning or playing strength. CUDA results are from one shared RTX 3060 host;
other hardware was not measured for this feature.
