# 0.7.0 — Fresh games and manageable records

New games use fresh randomness, compatible trained opponents are suggested from
saved evaluation evidence, and game/model collections can be cleaned up without
inventing results or losing completed history unexpectedly.

### Added and improved

- New games and restarts receive a fresh server-generated unsigned 32-bit seed.
  The saved game displays its base seed; AI decisions derive their seed from the
  base and move number. A single fixed-seed option supports explicit comparisons.
- AI workshop model cards display the recorded **Training seed**, distinct from
  evaluation and game seeds. Older imports without it show **Not recorded**.
- New-game AI sides preselect the compatible model with the best comparable
  baseline evaluation. The completion-aware score counts unfinished games as zero
  points; sample size breaks ties. When no comparable result exists, the newest
  compatible model is selected with a fallback explanation. Manual choices remain
  available and survive ordinary option refreshes.
- The Hall of records puts detailed statistics in a separate section above game
  history. History is collapsible, initially shows ten records and can show more.
  Shared filters keep the statistics and history consistent.
- Each game has a confirmed, version-checked delete action. Removing a record
  recalculates totals, rates, player/AI results and average game lengths from the
  remaining records. Deleting the current game clears its browser selection.

### Fix: a model appears permanently in use

The browser remembers one current game, but the server retains earlier unfinished
games too. Starting another game or changing browsers does not complete those
records, so a model can correctly remain referenced even when no active game is
visible in the current browser session.

The model-delete dialog now lists its server-side unfinished references. You can
resume/remove those games, or explicitly check **Discard unfinished games and
delete model**. That choice removes the unfinished games without history or
results. Completed records, historical model labels, other games and original
training checkpoints remain. Running tournaments still require stopping first.

### Integrity

- Model usage is checked before confirmation. A usage fingerprint prevents the
  browser from discarding new or changed references without renewed review.
- Registry deletion failures roll back pending game removals. Ordinary game deletion
  checks the displayed version, and late AI requests cannot recreate removed records.
- Completed-game detection uses the recorded outcome independently of replay position.
- Legacy game records retain their original seed behavior; training and tournament
  experiments retain their explicit reproducibility settings.
- No schema migration is required; the database remains at schema 3.

### Validation

- **252 Python tests**, **35 frontend unit tests** and **16 real-API browser checks
  passed**. Four duplicate mobile worker checks are intentionally skipped; mobile
  seed/history/statistics management runs.
- Tests cover explicit/fresh seeds, legacy behavior, ranking and manual choices,
  version guards, recalculated rates/averages, changed-usage consent, deletion
  rollback, replayed completed games and late in-flight AI responses.
- Actual CPU training verifies training-seed display, compatible default selection,
  hidden unfinished-game cleanup and retained completed replay/checkpoints.
- Ruff/Prettier, mypy/TypeScript and the production build pass.
- Desktop/mobile visual checks verify the separate statistics panel, readable values
  and explicit cleanup confirmation. Production startup preserves all seven existing
  game records exactly and continues using schema 3.

### Update

Stop the service and back up the full data directory, then update and restart:

```sh
make install
make build
bash scripts/start.sh
```

Existing records are preserved during startup. Deleting a game or opting to
discard unfinished model references is an explicit action in the new UI.
See `docs/PERSONALIZATION.md` for the settings and collection-management behavior.
Model ranking reflects stored evaluation evidence and does not establish absolute
playing strength or comparability across different evaluation budgets.
