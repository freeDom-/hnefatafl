# 0.41.1 - Deployment-safe tournament settlement recovery

This hotfix corrects a release-blocking production startup regression introduced
in `0.41.0`. It contains no feature, database-schema or frontend-behavior change.
The online schema remains **21**, account schema **9**, checkpoint tensor format
**1** and job-archive schema **3**.

## Root cause

`0.41.0` added durable player-tournament settlement. Its FastAPI lifespan called
the one-time startup reconciliation synchronously, and that reconciliation took
the shared, non-blocking deployment write gate through `OnlineCore._write()`.

The production updater deliberately holds the **exclusive** `.deployment-gate`
flock from before service shutdown through activation, readiness verification and
commit. The new service therefore failed its own lifespan while the updater was
waiting for readiness:

```text
OnlineError: Deployment in progress. Please retry shortly.
ERROR: Application startup failed. Exiting.
```

The updater then correctly diagnosed failed readiness and restored the previous
release. The defect occurred even with no player tournaments because startup
reconciliation ran unconditionally.

## Corrected recovery lifecycle

- Startup still attempts reconciliation immediately when no deployment is in
  progress. A genuine database, integrity or programming failure still fails that
  synchronous attempt.
- Expected exclusive-gate contention is now a distinct `DeploymentLocked` error.
  It leaves durable tournament queue rows untouched, logs once, and lets the
  lifespan start normally.
- The existing tournament settlement worker retries deferred reconciliation after
  the gate is released. It performs startup reconciliation **once successfully per
  worker lifecycle**, then resumes normal due-start and settlement polling.
- Retries are bounded to the worker's one-second poll, use bounded backoff for
  unexpected failures, do not mark failed recovery as complete, and stop on
  shutdown. Repeated scheduled reconciliation is not performed during normal
  polling.
- Partial lifespan startup failures now shut down any workers that were already
  started, including account mail and online expiry workers.

The deployment lock, its inode, write-gate checks, CSRF/authentication policies,
background-worker freeze and scheduled tournament starts are unchanged. The
hotfix does not require a new deployment manager: an update initiated by the
already installed `0.40.0` updater holds the same lock and uses the same health,
authenticated-read and anonymous-rejection probes.

## Readiness diagnostics

Readiness failures now report sanitized diagnostics instead of only:

```text
Service readiness failed; inspect journalctl -u hnefatafl
```

The report includes deployment phase and target version, failed probe, category
and last HTTP status, transport classification (connection refused, timeout,
connection error, invalid JSON or unexpected health response), attempt count,
elapsed time, allowlisted systemd `ActiveState`/`SubState`/`Result`/exit status,
whether automatic recovery succeeded or failed, and the journal/transaction
inspection commands. It never includes credentials, cookies, CSRF tokens,
response bodies, configuration secrets, personal data or GitHub tokens.

## Validation

The regression suite adds a real FastAPI lifespan under a real exclusive file
lock, with both empty and populated tournament databases. It verifies health and
authenticated reads, anonymous rejection, blocked HTTP and tournament mutations,
deferred worker retries, automatic settlement after release, idempotent repeated
reconciliation, restart and shutdown while deferred, due scheduled starts under
the lock, and propagation of genuine database errors.

Disposable deployment integration covers fresh installation, a schema-20 update
through the real activation/probe/commit sequence, ordinary schema-21 restart,
failed activation with automatic rollback, and explicit recovery of an interrupted
activation. Readiness diagnostic tests cover refusal, timeout, unexpected status,
invalid/unexpected health bodies, transient recovery, successful rollback and
rollback failure, including checks that a private response body is not emitted.

`make deployment-check` is now a mandatory CI step before the complete backend
suite. Exact local and CI results are recorded separately in the pull request and
[Validation](../VALIDATION.md).

## Compatibility and limitations

The change is additive at runtime and requires no schema migration. Existing
schema-20/21 databases, accounts, permissions, model files, training jobs,
checkpoints, historical games, player tournaments, settlement queues and rating
records are retained. No maintenance-mode flag is introduced.

As with every release, the service and remote workers must run the exact same
version. Real Proxmox/systemd activation, an update performed by the previously
installed `0.40.0` updater, and a rollback on a target host still require
target-host validation; the disposable integration tests use an in-process HTTP
transport and fake systemd actions, so they do not establish host-specific
systemd, proxy, storage or restart behavior.
