# 0.41.1 - Deployment-safe tournament settlement recovery

This hotfix corrects a release-blocking production startup regression introduced
in `0.41.0`. It contains no feature, database-schema or frontend-behavior change.
The online schema remains **21**, account schema **9**, checkpoint tensor format
**1** and job-archive schema **3**.

## Root cause

`0.41.0` added durable player-tournament settlement. Its FastAPI lifespan called
the one-time startup reconciliation synchronously, and that reconciliation took
the shared, non-blocking deployment write gate through `OnlineCore._write()`.

The production updater deliberately holds the **exclusive** `.deployment-gate`
flock from before service shutdown through activation, readiness verification and
commit. The new service therefore failed its own lifespan while the updater was
waiting for readiness:

```text
OnlineError: Deployment in progress. Please retry shortly.
ERROR: Application startup failed. Exiting.
```

The updater then correctly diagnosed failed readiness and restored the previous
release. The defect occurred even with no player tournaments because startup
reconciliation ran unconditionally.

## Corrected recovery lifecycle

- Startup still attempts reconciliation immediately when no deployment is in
  progress. A genuine database, integrity or programming failure still fails that
  synchronous attempt.
- Expected exclusive-gate contention is now a distinct `DeploymentLocked` error.
  It leaves durable tournament queue rows untouched, logs once, and lets the
  lifespan start normally.
- The existing tournament settlement worker retries deferred reconciliation after
  the gate is released. It performs startup reconciliation **once successfully per
  worker lifecycle**, then resumes normal due-start and settlement polling.
- Retries are bounded to the worker's one-second poll, use bounded backoff for
  unexpected failures, do not mark failed recovery as complete, and stop on
  shutdown. Repeated scheduled reconciliation is not performed during normal
  polling.
- Partial lifespan startup failures now shut down any workers that were already
  started, including account mail and online expiry workers.

The deployment lock, its inode, write-gate checks, CSRF/authentication policies,
background-worker freeze and scheduled tournament starts are unchanged. The
hotfix does not require a new deployment manager: an update initiated by the
already installed `0.40.0` updater holds the same lock and uses the same health,
authenticated-read and anonymous-rejection probes. Genuine cross-version coverage
extracts the pinned `0.40.0` updater/application and schema-20 historical code,
creates an authentic schema-20 database with that code, and runs the old updater
against a corrected Uvicorn release under the real exclusive lock.

The `0.40.0` updater cannot repair its own generic diagnostics or enforce the new
rollback policy; those improvements run only when the corrected updater code is
executing. An update initiated by the old updater still gains the target
application's startup fix.

## Known-incompatible rollback policy

`0.41.0` itself cannot start while the exclusive deployment gate is held, so it is
not a safe rollback target. The corrected updater rejects recorded rollback and
interrupted-recovery targets of `0.41.0` **before** stopping the running service,
restoring a snapshot or switching the release symlink:

- an explicit `--rollback` to `0.41.0` is refused with operator guidance;
- an interrupted transaction whose previous release is `0.41.0` is refused before
  any service/data/symlink change;
- during automatic recovery from a failed update, the failed target service is
  stopped, then rollback to `0.41.0` is refused without restoring the snapshot,
  switching back or starting the incompatible release. The transaction journal,
  backup reference, current target release and persistent data are retained for
  reviewed manual recovery.

Ordinary rollback to `0.40.0` remains supported where existing schema and
data-authority rules permit it. Rollback between corrected releases containing
tournament background workers is also supported. Historical `0.41.0` code is not
modified, and no downgrade mechanism or gate bypass is introduced.

## Readiness diagnostics

Readiness failures now report sanitized diagnostics instead of only:

```text
Service readiness failed; inspect journalctl -u hnefatafl
```

The report separates the original deployment target, previous release, currently
probed release, recovery target and installed release; it also identifies the
failed phase (stopping, snapshot, migration, activation, service startup,
readiness or commit) and the failed automatic-recovery step. Health probing
retries truncated responses and HTTP protocol errors within the existing budget;
authenticated and anonymous probes report the same sanitized categories. The
report includes probe category, last HTTP status, transport classification
(connection refused, timeout, connection error, truncated response, HTTP protocol
error, invalid JSON or unexpected health response), attempt count, elapsed time,
allowlisted systemd `ActiveState`/`SubState`/`Result`/exit status, whether
automatic recovery succeeded or failed, and the journal/transaction inspection
commands. It never includes credentials, cookies, CSRF tokens, response bodies,
exception payloads, configuration secrets, personal data or GitHub tokens.

## Validation

The regression suite adds a real FastAPI lifespan under a real exclusive file
lock, with both empty and populated tournament databases and the complete
account-mail/online/tournament worker lifecycle. It verifies health and
authenticated reads, anonymous rejection, blocked HTTP and tournament mutations,
deferred worker retries, automatic settlement after release, idempotent repeated
reconciliation, restart and shutdown while deferred, due scheduled starts under
the lock, partial-startup worker cleanup and propagation of genuine database
errors.

Genuine cross-version tests use pinned historical Git objects, never committed
source copies: actual `0.40.0` updater/application code, historical schema-20
migration code and a corrected target release. They verify the old updater holds
the real exclusive lock, activates and probes the corrected Uvicorn application,
and preserve representative accounts/permissions, models, training jobs,
checkpoints and historical games. Both direct authentic schema 15→21 and
historical schema 20→21 upgrades are covered; the schema-20 scenario additionally
preserves online/player-tournament records. Post-commit tests authenticate and
perform a protected mutation through the actual target release. A separate genuine
test starts the actual `0.41.0` application under the exclusive gate and records
its original `OnlineError` failure.

A deterministic post-migration readiness failure is injected through disposable
data (administrator deactivation after the target is healthy). The actual
historical `0.40.0` updater then refuses cross-schema snapshot restoration with
`Online schema changed; manual recovery is required`, retains the activated target
and schema-21 live database, preserves the verified schema-15/20 snapshot, model
and checkpoint files and transaction metadata, and does not start the old
application. The corrected updater's explicit rollback performs a read-only
schema preflight and refuses the same mismatch before service stop, data
replacement or symlink switching. Compatible matching-schema rollback between
corrected releases remains tested and supported.

Fast in-process lifecycle tests remain for fresh installation, ordinary restart,
failed activation/rollback and interrupted recovery; they are explicitly labeled
as simulations because every release directory executes the current checkout.
Readiness diagnostic tests cover refusal, timeout, truncated responses, HTTP
protocol errors, unexpected status, invalid health bodies, transient recovery,
release/phase identification, malformed metadata, policy rejection, schema
preflight/refusal, successful rollback and rollback failure. Deliberate
operator-facing errors retain their messages; unexpected exception strings
containing synthetic credentials/session values are not exposed. Subprocess
cleanup tests use the exact PID-file derivation and verify the application process
is gone after success, readiness failure and harness timeout.

Local focused results for this preparation: deployment/lifecycle **63 passed**,
cross-version **6 passed**, player-tournament and security **149 passed**; Ruff,
format, mypy, documentation and the production frontend build passed. The complete
backend/browser suite is delegated to CI. `make deployment-check` is mandatory in
the Python job, and a dedicated CI job builds the frontend, fetches the pinned
historical refs and runs the cross-version suite. Exact CI results are recorded in
the pull request and [Validation](../VALIDATION.md).

## Compatibility and limitations

The change is additive at runtime and requires no schema migration. Existing
schema-20/21 databases, accounts, permissions, model files, training jobs,
checkpoints, historical games, player tournaments, settlement queues and rating
records are retained. No maintenance-mode flag is introduced.

As with every release, the service and remote workers must run the exact same
version. Real Proxmox/systemd activation, reverse proxying and destructive
rollback on a target host still require target-host validation. The cross-version
subprocess tests replace only systemd/privilege orchestration; they use real
locking, HTTP probing, Uvicorn processes, migration and snapshots, but do not
establish host-specific systemd, cgroup, proxy, storage or restart behavior.
Historical release source is fetched by pinned commit/tag from the trusted origin;
it is not committed to this repository.

An updater executing from historical `0.40.0` code cannot enforce the new
known-incompatible rollback policy or emit the enhanced diagnostics. Those
protections apply once the corrected `0.41.1` updater is installed.
