# 0.35.0 - Custom single-player opponents, training help and parallel CPU search

This feature release builds on `0.34.0` with an administrator-only custom AI
opponent for single-player games, an accessible explanation for every training
parameter, a redesigned opt-in parallel CPU search that no longer bounds game
concurrency, and a large reduction in parallel evaluation progress traffic.

Upgrading from `0.34.0` requires **no database migration**: SQLite stays at schema
**13**, and no tournament, job, model or checkpoint record changes format. The new
`search_workers` setting is capability-negotiated, so a legacy remote worker keeps
its existing behaviour and never receives the key. Update remote workers to `0.35.0`
before assigning jobs that request a positive worker count.

Full comparison: [`0.34.0...0.35.0`](https://github.com/freeDom-/hnefatafl/compare/0.34.0...0.35.0).

## Added features

### Custom single-player AI opponents

Administrators can now configure a fully custom AI opponent when starting a
single-player game (PR #48). **Custom opponent** appears in the New Game dialog for
administrators only, in Human-vs-AI mode only, and exposes the same participant
configuration as a tournament: algorithm, trained model, search wrapper, heuristic,
alpha-beta search optimizations and search budgets.

- A custom opponent and a tournament participant are the same configuration. Both
  use the shared `resolve_ai_config` validation, the same catalog profiles and the
  same nested alpha-beta `search` object, so a setting added for tournaments is
  available to a custom opponent without a second implementation. The frontend
  editor was extracted into one `AgentConfigFields` component that both dialogs
  render.
- The configuration is validated server-side, instantiated as the real requested
  agent, used for every opponent move and stored with the game, so reload, resume
  and restart reproduce it instead of silently reverting to a named preset. Legacy
  records without a stored creation request keep the previous restart path.
- A non-empty custom configuration requires the `all_data` permission, enforced in
  the game-creation transaction before the record is written; the UI restriction is
  not the security boundary. Unknown fields, malformed types, out-of-range budgets,
  unsupported algorithm/wrapper combinations and missing, unregistered,
  checkpoint-less or wrong-ruleset models are rejected with a named error, and
  `model_path` is never accepted from the browser API.
- Named presets (Shield bearer, Shield maiden, Jarl, Seer) remain available to every
  player and stay authoritative over any configuration supplied beside them. The
  stored creation request is hidden from `/api/games` responses.
- The trained-model catalogue is loaded lazily, only while a visible custom seat
  needs it. **Refresh models** reloads it without reloading the application, so a
  model registered, renamed or deleted while the dialog is open appears on the next
  refresh. Concurrent refreshes publish the newest request's result, so an older
  response can never replace fresher data; a failed or malformed response keeps the
  previous list selectable and shows a non-blocking retry. Hiding a configuration
  cancels an in-flight request and keeps the unsaved settings for when the seat
  returns.
- A browser preference never stores a custom identity or configuration; only the
  battlefield, mode, side and preset are remembered.

See [AI opponents](../AI.md#custom-opponents) and
[single-player setup](../GAMEPLAY.md).

### Training parameter help

Every configurable training parameter now explains itself (PR #49). The **Create New
Training Job** form and the **Resume Training Job** dialog render an information
button beside every parameter label, and the immutable checkpoint values in the
resume summary carry the same help.

- Hovering the label or the button, focusing the button with the keyboard, or
  tapping it reveals a parameter-specific description: what the value controls,
  which phase it affects (self-play, gradient training or evaluation), how changing
  it affects behaviour, how it interacts with other settings, and where units,
  ranges or defaults matter.
- Conditional settings, the collapsed **Advanced configuration** section and the
  tuning-only study controls are covered, as are the resume summary's read-only
  Battlefield, Network channels, Residual blocks, Random seed and Optimizer values.
- An activation pins the description so it survives the pointer leaving; a second
  activation, Escape or a press elsewhere dismisses it. An ordinary description
  never takes focus, while a description taller than the visual viewport becomes a
  focusable, scrollable region so the whole text stays reachable with mouse wheel,
  touch and keyboard instead of being clipped. Neither traps focus or changes a
  value.
- `frontend/src/trainingTooltips.ts` is the single registry, keyed by the same
  parameter identity the API and the form controls use, so a parameter that appears
  in both forms is described identically. A coverage test enumerates the fields each
  form renders — including conditional, advanced, tuning-only and read-only ones —
  and fails when one has no description, and the German copy is checked for parity.
- The information button keeps a meaningful accessible name (`Explain {field}`) and
  points at the full description, and width/height are constrained to
  `visualViewport`, so pinch-zoom and a mobile keyboard keep the help inside the
  visible area.

See [parameter help](../TRAINING.md#parameter-help-in-the-forms).

## Performance

### Parallel CPU search

`search_workers` (default 0, still opt-in) was redesigned so the worker count sizes
CPU parallelism only and no longer bounds game concurrency (PR #39). Two worker
processes can now drive up to the configured `self_play_concurrency` or
`evaluation_concurrency` instead of two games.

- One shared scheduler, `hnefatafl/cooperative.py`, drives in-process self-play,
  in-process evaluation and every spawned actor, so all three paths interleave games
  identically. Each actor multiplexes many game contexts and evaluates its own
  leaves in one batched forward pass (CPU, frozen read-only snapshots, one math
  thread).
- CUDA/OpenVINO models, tensors, streams and caches stay in the parent. The parent
  merges the outstanding requests of the whole pool into as few forward passes as
  the batch limit allows and routes every result back by explicit request token. It
  waits for a sibling actor only inside a bounded merge window (8 ms by default) and
  stops the moment that sibling delivers; it never delays a batch purely to fill it.
- `search_workers` is a cap, not a target: processes are created on demand only as
  far as a phase has concurrent game slots, reused by later phases, and never
  started for an idle slot. Game indices are assigned to workers round-robin and
  statically, which makes batch composition, and therefore the CPU work fingerprint,
  reproducible.
- `self_play_concurrency` and `evaluation_concurrency` are hard upper bounds across
  the whole pool. Capacities come from a quotient/remainder split of the requested
  concurrency, so they sum to exactly the requested limit. An explicit
  `sequential` self-play or evaluation mode always runs in-process; `batched` and
  `auto` use the pool whenever workers are configured, and `auto` otherwise batches
  on CUDA/OpenVINO and stays sequential on CPU/MPS. A configuration with both phases
  sequential starts no worker processes at all.
- Ordered replay stays bounded: with `retain_examples=False` the pool grants each
  worker one slice at a time and only while the started-but-uncommitted count stays
  inside the replay window, and it keeps only a completion count rather than a copy
  of every result, so retained memory is bounded by active concurrency instead of
  the iteration's game count.
- Worker startup is exception-safe per attempt, evaluation backends the pool creates
  are closed exactly once on success, cancellation or failure, and inference-cache
  occupancy is reported once per bound weight generation instead of once per granted
  slice.
- Actors report live progress as they search, batched into bounded messages; the
  parent applies each batch as a delta and drops a message whose per-worker sequence
  it has already seen, so positions and simulations are never counted twice and the
  dashboard advances during a long game instead of waiting for it to finish. The
  initial self-play active-game count is announced before the first expensive move.

Measured independently against `0.34.0` `main` on CPU (Brandubh/Tablut/Copenhagen,
one math thread per process, median of three alternating pairs): evaluation
**2.26× / 1.85× / 2.18×** and self-play **1.21× / 1.25× / 1.46×** at two workers,
and evaluation **2.44× / 2.12× / 2.66×** and self-play **1.33× / 1.46× / 1.58×** at
four workers. Every CPU arm of every scenario produced exactly one work fingerprint
equal to the `main` baseline's, so the parallel path is exact on CPU. On an RTX 3060
CUDA host the worker arms are about **7% slower** than `search_workers=0` on the
64-game self-play workload (0.93×) while restoring average batch occupancy to
~21 states per forward pass, and CUDA evaluation shows no established speedup and no
regression within the host's roughly ±30% measurement spread. GPU training therefore
keeps the recommended `search_workers=0` unless traversal is the measured
bottleneck. See
[the redesigned scheduler measurements](../benchmarks/training-parallel-search-redesign.md)
and [reading performance metrics](../PERFORMANCE.md#reading-performance-metrics).

### Evaluation progress reporting

Parallel evaluation previously emitted one progress IPC message per neural inference
batch, defeating the actor-side batching bounds (PR #50). Evaluation now reports on
a nominal one-second wall-clock interval with a 16,384-leaf work cap, while
self-play keeps its one-message-per-played-move cadence. This is not a strict rate
limit: game completion, slice end, cancellation and failure flush immediately, so
the final delta is never dropped.

Measured against the previous implementation on a CPU Brandubh workload: progress
messages fall **170×** at two workers and **181×** at four workers in the historical
collection, and about **150×** in the paired follow-up runs, while neural
evaluations, inference forward passes and the evaluation work hash stay identical.
The removed monitoring cost is roughly **5–9%** of a phase's runtime in the paired
before/after comparison and sits below host noise afterwards. Parent-side
monitoring still updates at least once per second while search runs and immediately
on each game completion. The change is internal; no configuration or frontend
control was added. See
[the evaluation progress measurements](../benchmarks/training-evaluation-progress.md).

## Interface and API changes

- `POST /api/games` accepts the same optional `config` participant object as
  `POST /api/tournaments`, validated by the shared `resolve_ai_config`. The stored
  creation request is never returned by `/api/games`.
- Remote workers advertise a `parallel_search` boolean capability. A worker without
  it can still claim jobs that leave `search_workers` at its default, and resume
  downloads strip the key from a legacy worker's configuration, while an explicit
  positive worker count requires an updated worker.
- `search_workers` is part of the shared training field vocabulary
  (`frontend/src/trainingContract.json`) and the remote training field set.
- A parallel phase adds bounded performance metrics: `search_workers`,
  `search_worker_count`, `search_concurrency`, `search_worker_capacity`,
  `search_worker_peak_active`, `search_replay_window`, `search_flush_seconds`,
  `search_initialization_seconds`, `search_progress_messages` (with per-worker,
  trigger-reason, position and send/handle breakdowns) and `inference_location`.
- A registered model may back an alpha-beta tournament or custom opponent; the
  alpha-beta optimizations are available for a neural opponent that uses the
  alpha-beta wrapper. Because a neural value head is not guaranteed
  D4-equivariant, a model-backed search disables the symmetry switches and the
  server rejects them if they arrive.

## Upgrade and installation

1. Stop/cancel active training and tournaments and pause remote claim loops. Take a
   complete stopped-writer backup of the data root and protected configuration,
   retaining matching `0.34.0` code.
2. After `0.35.0` is published as a stable release with its verified archive digest,
   use the production updater:

   ```sh
   hnefatafl-update --check
   hnefatafl-backup
   hnefatafl-update --version 0.35.0
   ```

   On a Proxmox host, prefix these commands with `pct exec <CTID> --`. Fresh
   installations follow [Deployment](../DEPLOYMENT.md). A branch, tag or GitHub
   automatic source archive is not a production installation asset.
3. Confirm schema **13** and application readiness. This release adds **no database
   migration**: tournaments, training jobs, games and accounts keep their existing
   tables and records. An existing single-player game without a stored creation
   request keeps its previous restart path.
4. Update remote workers to **0.35.0** before assigning new work that requests
   `search_workers`. The capability is negotiated: a legacy worker keeps its
   existing execution mode and never receives the unknown key, while an explicit
   positive worker count requires an updated worker. Other settings are unchanged.
5. `search_workers` remains opt-in and defaults to 0. On CPU it parallelizes
   evaluation and self-play traversal; on CUDA it preserves batch occupancy but was
   not faster than the single-process scheduler on the measured host, so keep 0
   there unless traversal is the bottleneck. Custom opponents require an
   administrator account and a registered model whose ruleset matches the
   battlefield.

No model or checkpoint format changed (tensor format 1), and no runtime
configuration key was removed or renamed. Schema-13 code from `0.34.0` remains
compatible, so a rollback needs no reverse migration.

## Limitations

- A custom opponent is offered to administrators only and in Human-vs-AI mode only;
  AI-vs-AI keeps the named presets. Its configuration cannot be re-selected from
  browser preferences, because identities and configurations are deliberately never
  restored from browser storage. Deleting a model that an unfinished custom game
  uses is still refused (409) with the existing "discard unfinished games" flow, and
  an out-of-band registry removal is reported as `Model not found.` on the next
  opponent move.
- Training tooltips explain the implementation and deliberately avoid quoting
  performance numbers, which depend on hardware. Chromium page-scale emulation
  approximates pinch-zoom rather than reproducing a physical gesture, and physical
  Safari was not exercised by these runs.
- `search_workers` remains opt-in. On GPU, trajectories are not bit-reproducible
  across runs or worker counts because batch shape depends on when sibling actors
  deliver, and the resulting `1e-8` numerical difference can select a different move
  thousands of decisions later; use `search_workers=0` when a GPU run must be
  bit-identical. CPU is exact. The 8 ms merge window is tuned on the 64-game
  workload, and smaller GPU workloads are dominated by their drain tail where
  merging cannot help.
- Parallel-search performance was measured on one 12-core WSL2 CPU host and one
  RTX 3060 host. Absolute times are workload- and host-specific; batch occupancy and
  the direction of the changes are the portable results. MPS was not measured, and
  CUDA evaluation timings carry roughly ±30% spread between repeated pairs of the
  same configuration, so those comparisons establish "no regression" rather than a
  speedup.
- Evaluation progress measurements scale the full 64-game workload down for a
  4-core CPU-only host; the per-batch message rate is scale independent, but the
  wall-clock benefit is below that host's run-to-run noise. GPU/OpenVINO and
  remote-worker execution were not re-benchmarked, because the change is parent/actor
  IPC and does not alter inference backends or the remote protocol.
- Parallel search and evaluation progress batching are throughput and
  work-avoidance changes. No playing-strength or model-quality improvement is
  claimed, and no new pretrained model is included.
