# 0.32.0 - Online multiplayer, verified accounts and interface scale

This feature release adds authenticated online play, email verification and
password recovery, per-ruleset Elo leaderboards, and a personal Dashboard. Shared
play screens, larger boards and saved interface scales reduce desktop chrome.

Upgrading from `0.31.0` advances SQLite from schema **8 to 12**. Public registration,
online admission and automatic timeout finalization require separate operator
configuration; installing the release does not enable them.

## Delivered behavior

### Accounts and recovery

- Optional public registration creates an active, unverified USER account without
  logging it in. Users explicitly verify their email and log in; an unverified
  account can still use authenticated single-player.
- Verification and password-reset links are purpose-bound, expiring and single-use.
  Resend replaces the previous link. A password reset revokes existing sessions
  and requires a new login; it does not verify an account or reactivate a disabled
  one. Existing account IDs, roles, hashes and ownership survive migration.
- SMTP delivery uses a durable leased queue, bounded retries and shared abuse
  budgets. Email delivery is not exactly once: an older delayed message may arrive,
  but only the current link works. Login, registration, verification and recovery
  share accessible English/German form layouts.

See [registration and mail operations](../REGISTRATION.md).

### Durable online games

- Verified, active accounts can create or join Brandubh, Tablut and Copenhagen
  games when admission is enabled. The authenticated lobby has **All games**,
  **My games** and **My turn** tabs with bounded pagination and automatic refresh.
- Match modes are a single game or two games with swapped sides, activated
  simultaneously or sequentially. Random sides are assigned once at join.
  Rules, sides, match mode and time control freeze at creation.
- Server-owned per-move clocks default to three days and accept integer durations
  from one minute to fourteen days. The browser provides Days/Hours/Minutes
  controls. Logout, disconnect and restart do not pause or reset deadlines.
- SQLite transactions persist seats, legal moves, versions, deadlines and effective
  results together. Stale writes conflict; reconnect reloads authoritative state.
  Uncertain creation requests retain their exact request ID/settings for deliberate
  recovery rather than silently creating another match.
- Cancellation, concession, engine completion, timeout processing and audited
  administrative voids have distinct outcomes. A persistent timeout gate applies
  to request and background processing and starts paused. Online quotas default
  to five waiting lobbies and ten creations per fifteen-minute window per account;
  administrator monitoring exposes bounded denial counts and database growth.
- The active-game switcher spans online and account single-player games. Both use
  the same details, armies, captured-pieces, result and board/toolbar sections.
  A captured king can remain visible at its final square without changing engine
  occupancy or legal moves.

See [online controls](../ONLINE_PLAY.md) and [online operations](../ONLINE.md).

### Ratings and recorded games

- All newly created online games are rated; explicit unrated creation is rejected.
  Historical casual games keep their policy and are not backfilled. Only eligible
  human-vs-human online results contribute; AI, training and single-player do not.
- Each ruleset has an Elo pool starting at `1500`, with fixed `K = 32` and a
  provisional marker before ten eligible games. Each leg of a two-game match is
  rated separately. Concessions and finalized timeouts count; cancelled and voided
  games do not. A void withdraws the event and deterministically rebuilds the pool.
- Immutable start-rating snapshots are captured at activation. Recorded rows show
  those ratings when available and the winner's effective positive Elo delta.
  Earlier records never invent start ratings from today's standings.
- One authenticated leaderboard orders the displayed Elo, completed rated-game
  count and immutable account ID. Dashboard embeds a compact view; full standings
  are paginated. The selected ruleset is saved locally, initially Copenhagen.
- Dashboard becomes the landing page for new/resumed games, personal ruleset
  statistics and recent records. The two statistics cards start collapsed and
  expand independently; expansion is not saved. AI-vs-AI account games remain for
  administrator analysis and do not enter personal history/statistics.
- Hall records use server filters and independent, read-only selected reviews.
  Normal users see participating online records; authorized administrators can
  inspect online and account single-player categories. Viewer-local replay and
  playback never seek or overwrite the authoritative game.
- Completed online reviews support the online-scoped move advisor and winning
  chances. Active, waiting, cancelled and voided online games never grant analysis;
  a client countdown reaching zero is not completion. Review authorization is
  checked separately from the list.

See [rating policy](../RATINGS.md) and [Dashboard and Hall](../DASHBOARD.md).

### Single-player and appearance

- New account games bind the human seat to the signed-in account. Normal users
  play a fixed Shield bearer, Shield maiden, Jarl or Seer preset; administrators
  can also create AI-vs-AI games. The normal setup no longer creates local profiles
  or arbitrary custom/model configurations. Historical setups remain readable and
  playable; Restart is limited to unfinished games allowed by the current policy.
- Local-player CRUD and its UI are removed while retaining historical identities
  and records. Existing training, model and tournament administration remains.
- **Appearance → Interface scale** saves **Compact / Default / Large** in the
  browser. It scales spacing and text independently of color, board and token
  themes, restores before first paint, and defaults safely for older preferences.
  Sixteen stylesheets share spacing tokens and responsive scale settings.
- The redundant play heading remains available to screen readers and programmatic
  focus. Desktop play uses the available height, including wrapped administrator
  navigation; tall side panels scroll internally. Mobile retains document scrolling.
  Board width remains stable across game-state and document-height changes.
- Measured board-frame widths on both play modes are **804/711/615 px** at
  1920×1080 and **509/416/320 px** at 1568×785 for Compact/Default/Large.
  All twelve combinations fit the document viewport without horizontal overflow
  or battlefield/footer overlap.

See [gameplay](../GAMEPLAY.md) and [appearance preferences](../PERSONALIZATION.md).

## Upgrade and installation

1. Stop/cancel active local/remote training and tournaments, and pause remote claim
   loops before updating. For an existing online deployment, pause the persistent
   timeout gate before maintenance; clocks are retained, not extended.
2. Take a complete stopped-writer backup of the data root and protected
   configuration, including the database, jobs, models and tournament artifacts.
   Retain matching pre-upgrade code. Using the new code against an isolated
   snapshot, run the read-only identifier-collision preflight before migration:

   ```sh
   .venv/bin/python -m hnefatafl.accounts check-collisions --data-dir /absolute/snapshot
   ```

   Resolve reported normalization collisions explicitly. Never merge account IDs
   or ownership by email. See [migration and rollback boundaries](../REGISTRATION.md#migration-and-rollback-boundary).
3. After `0.32.0` is published as a stable release with its verified archive digest,
   use the installed production updater:

   ```sh
   hnefatafl-update --check
   hnefatafl-backup
   hnefatafl-update --version 0.32.0
   ```

   From a Proxmox host, invoke the same commands with `pct exec <CTID> --`.
   Fresh installs follow [Deployment](../DEPLOYMENT.md); a branch, tag or GitHub's
   automatic source archive is not a production installation asset.
4. Confirm schema **12** and readiness after migration. Account verification starts
   unknown/unverified for legacy accounts; this preserves login/single-player but
   requires verification before new online admission, including administrators.
   No historical player ownership, online result or rating is invented.
5. Configure trusted HTTPS origin and SMTP before enabling public signup through
   `HNEFATAFL_REGISTRATION_ENABLED`. Online admission separately requires
   `HNEFATAFL_ONLINE_ENABLED`. Automatic timeout finalization additionally requires
   `HNEFATAFL_ONLINE_TIMEOUT_POLICY_APPROVED` and an explicitly enabled persistent
   gate after an approved outage procedure. Keep these gates disabled until their
   operational prerequisites are met.
6. Update remote workers to **0.32.0** before accepting new work. Exact application
   version, known revision and hardware compatibility still govern matching;
   an administrator override remains explicit and audited. Existing valid leases
   follow the documented restart policy. See [worker upgrades](../REMOTE_TRAINING.md#application-compatibility-and-upgrades).

Schema 8/9/10/11 code cannot read schema 12 safely. Forward migration is not an
automatic downgrade path to `0.31.0`. Compatible schema-12 recovery preserves live
account security, authoritative online rows and rating state, revokes sessions,
links/mail and worker credentials, and pauses timeout finalization. Cross-schema
recovery fails closed; use a forward repair or separately reviewed manual
reconciliation. See [online backup and recovery](../ONLINE.md#migration-backup-and-recovery).

No model-weight/checkpoint format migration or new worker protocol is introduced.

## Limitations

- Production signup, mail delivery, online admission and timeout activation require
  operator configuration and review. Browser mail tests use an isolated fake
  mailbox; real SMTP/provider deliverability and target-host deployment remain
  operator validation.
- Online clocks keep running through outages. There is no automatic deadline
  extension, waiting-game expiry, aggregate match score, rewards or rating decay.
  Repeated-opponent farming is possible; moderation uses audited void/rebuild
  procedures rather than an automated anti-farming system.
- Play requires an authenticated server connection. Anonymous guest/offline play,
  automatic opponent matchmaking, distributed self-play and PostgreSQL tooling
  are not shipped.
- Browser coverage is Chromium desktop/mobile emulation. Physical Safari and
  classic-scrollbar desktops were not established by those runs. CUDA and Intel
  OpenVINO GPU execution were skipped where hardware was unavailable.
- These changes establish functional play, persistence, training compatibility and
  layout behavior, not stronger AI or a stronger pretrained model. Displayed winning
  chances remain uncalibrated position assessments.
