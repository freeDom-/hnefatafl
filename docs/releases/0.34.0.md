# 0.34.0 - Live training monitoring, fixed-role tournaments and faster training

This feature release builds on `0.33.0` with phase-independent live training
monitoring and heartbeats, fixed-role model comparisons, batched neural evaluation
and pure-engine/search fast paths, and substantially lighter training and
tournament collection loading.

Upgrading from `0.33.0` requires **no database migration**: SQLite stays at schema
**13**, and no tournament, job, model or checkpoint record changes format. Update
remote workers to `0.34.0` before assigning new work; the new evaluation settings
are capability-negotiated, so a legacy worker keeps its sequential behaviour.

Full comparison: [`0.33.0...0.34.0`](https://github.com/freeDom-/hnefatafl/compare/0.33.0...0.34.0).

## Added features

### Live training monitoring

The dashboard no longer waits for a whole unit of work to finish. A daemon thread
republishes a bounded `heartbeat.json` beside the retained `progress.json` about
once per second, while the retained history is still rewritten only on real
progress events. A single long self-play game, optimization epoch or evaluation
match therefore keeps timers and counters advancing instead of producing a
byte-identical file that looked frozen.

- Every phase reports its own elapsed duration and, where a unit exists, its own
  counters: **self-play** (completed and scheduled games, active games, searched
  positions, MCTS simulations), **model training** (completed and total
  optimization steps, current epoch, running policy/value loss means),
  **evaluation** (completed and scheduled games, wins, draws, losses, effective
  opponent) and **preparation, checkpointing and finalization** (phase and elapsed
  time only, because no meaningful unit counter exists there).
- Monitoring starts before any expensive initialization, so checkpoint loading,
  model construction, state restore and inference setup report `starting`,
  `loading_checkpoint`, `initializing`, `restoring_state` and
  `initializing_inference` with the elapsed time still advancing. A failure there
  ends the job as `failed` (or `pruned`) with the error recorded, and a
  cancellation is honoured at the first point where a checkpoint can be written.
- Durations are published as monotonic values and anchored by the browser with one
  local one-second ticker, so an unsynchronised or skewed worker clock cannot
  affect the display. A new phase restarts only the phase timer and a new iteration
  only the iteration timer; a completed, cancelled or failed job adopts the
  authoritative backend durations and stops advancing.
- Heartbeat states are informational and never change job management or outcome:
  **Worker active**, **Running, long operation** (fresh publication, no meaningful
  progress for two minutes), **Potentially stalled** (ten minutes), **No recent
  updates** (the training process published nothing for twenty seconds while its
  supervisor still reports), **Worker connection lost** (the server confirms a
  remote supervisor has not reported for twenty seconds; the job fails when its
  lease expires), **Monitoring connection unavailable** (the browser has not
  received monitoring data for twenty seconds, so the worker's state is unknown
  rather than failed) and **Waiting for a worker** (queued).
- A tuning study is monitored across its whole lifecycle. The study publishes
  `initializing_study`, `preparing_trial`, `between_trials` and `finalizing_study`
  with its own monotonic duration and the completed-trial counter, and the last
  trial's charts stay visible without presenting its finished phase or timers as
  live. Ownership of the job's files moves between the trial's monitor and the
  study's under the publication lock, and the study publishes `between_trials`
  before the Optuna work that follows a trial, so a slow storage operation never
  leaves the dashboard without a heartbeat. Each publisher carries its own run
  identity, so a heartbeat from an earlier trial or from the study can never
  overlay the other's snapshot or revive a terminal state.
- Remote workers republish the training process's live snapshot at a bounded
  cadence independent of their lease renewal and report the child's own publication
  age measured on the worker host. A connected supervisor forwarding an unchanged
  snapshot is therefore never mistaken for a fresh child heartbeat, and a repeated
  report of an unchanged child revision carries only the bounded liveness
  projection, so an unchanged history, metrics, model list or log tail is never
  retransmitted.
- Jobs recorded before these fields existed omit the heartbeat state, phase timer
  and counters instead of inventing values.

See [training dashboard](../TRAINING_DASHBOARD.md#live-monitoring) and
[remote training](../REMOTE_TRAINING.md).

### Fixed-role tournaments

- **Fixed-role comparison** pins one trained model as **Attackers** and one as
  **Defenders** for every scheduled game (PR #46). Choose exactly one battlefield
  and two trained models; the same model may fill both seats for a self-play
  comparison, and the two seats stay separate in every result.
- Both seats share exactly one **Shared search configuration** — wrapper,
  applicable parameters and move limit. The API, the headless runner and the
  configuration importer all normalise the two effective configurations and reject
  a pairing whose settings differ after excluding the model identity and the
  participant's own seed, so a request that bypasses the interface is refused too.
  Alpha-beta symmetry switches stay unavailable because a neural value head is not
  guaranteed to be D4-equivariant.
- Sides are never swapped, so the game count is the total number of scheduled games
  and odd counts are valid (1–100 accepted; the round robin still requires an even
  2–100). A deterministic seed is derived per scheduled game.
- The saved view reports side-specific results — games played, attacker wins,
  defender wins, rule draws, unfinished games, attacker and defender win and score
  rates over completed games, average game length and per-opponent search
  diagnostics — with a stacked outcome bar. These numbers are deliberately not a
  balanced overall-strength comparison.
- Mode is additive inside the saved configuration: a missing `mode` means
  `round_robin`, so every previously saved tournament keeps its behaviour and stays
  readable. No schema change and no migration. `mode` and the attacker/defender
  seat order appear in the API response and in the exported document, and each
  setup dialog accepts only its own mode.
- A registered model may now also back an MCTS or alpha-beta tournament participant
  (`algorithm` `mcts` or `alpha_beta` with `model_id`): the API, the importer and
  the headless runner keep the model and evaluate with the network.
- The headless `tournament --config FILE` command accepts both modes, validates
  portable participants exactly as the browser API does — naming the participant
  index and the offending field — and requires exactly one supported battlefield
  for `mode: "fixed_roles"`. The historical flattened participant layout stays
  accepted, but a single document may not mix the two representations.

See [tournaments](../TOURNAMENTS.md#fixed-role-comparison).

### Batched neural evaluation

- `evaluation_mode` selects `auto` (default), `sequential` or `batched`; auto
  batches CUDA and keeps PyTorch CPU/MPS sequential, preserving the historical
  behaviour on CPU. `evaluation_concurrency` (default 16) and
  `evaluation_batch_size` (default 32) are independent of the self-play settings,
  and each model — candidate and Champion — keeps its own inference queue and
  cache. Evaluation stays FP32, side-swapped pairs stay ordered, and the sequential
  path remains available as the reference (PR #37, integrated by PR #42).
- `evaluation_inference_backend` selects `pytorch` (default, the historical
  numerical backend) or `training`, which builds a fresh post-optimization OpenVINO
  graph when that backend is selected. An alternate backend records a separate
  benchmark identity, so results measured with different numerical backends are
  never merged, and the reported OpenVINO device is the one actually used.
- The settings work through creation, resume, configuration import and remote
  workers. Workers advertise `evaluation_batching`; a legacy worker keeps the
  sequential default and never receives unknown execution keys, while an explicit
  new mode requires the capability. Resume downloads apply the same filtering.
- Queue waiting counts against wall deadlines, so a batched run with a binding time
  limit completes fewer visits than a sequential one. Compare completed search work
  and cutoff counts, and keep deadlines non-binding when comparing move sequences.

Measured independently against `0.33.0` on CPU (Brandubh/Tablut/Copenhagen, eight
evaluation games, 32 visits, 16-ply limit): **1.42× / 1.56× / 1.34×** faster than
sequential with matching recorded outcome hashes. On an RTX 3060 CUDA host:
**9.70×** against Shieldbearer and **5.61×** against Champion, but the Champion
work hashes differed between the two modes, so equivalent Champion outcomes, scores
and promotion decisions are **not** established. See
[batched evaluation](../benchmarks/training-evaluation-batching.md) and
[GPU measurements](../PERFORMANCE.md#gpu-measurements-on-the-rtx-3060-host).

## Performance

### Engine and search fast paths

- Terminal adjudication and move-existence checks no longer build complete move
  lists: an allocation-free early-exit legal-move query, cached immutable board
  geometry and an encirclement early exit when one edge-accessible defender
  disproves total enclosure. Move order, restricted-square pass-through, captures,
  repetition and no-move outcomes are unchanged (PR #38, integrated by PR #42).
- The optimized alpha-beta search (Jarl) builds interior successors on demand in
  frozen transposition/killer/history priority groups, keeping the upfront shuffle
  and stable static order within each group. Root and legacy construction remain
  eager, and searched nodes, values and moves at equal depth are identical to the
  eager reference (PR #41, integrated by PR #42).

Measured independently against `0.33.0` on CPU: successor generation
**2.86× / 5.27× / 2.58×** and real batched self-play **1.11× / 1.08× / 1.31×**
(Brandubh/Tablut/Copenhagen) with all successor and self-play work hashes matching;
fixed-depth Jarl search **2.11× / 3.93× / 11.04×** and training Jarl evaluation
**2.50× / 3.16× / 6.04×** with identical searched nodes and values. In the same GPU
batched self-play workload the engine change was 1.232× as a ratio of medians, but
one of three pairs showed no improvement, so the median paired gain (~1.056×) is
the conservative reading. See
[engine fast paths](../benchmarks/training-engine-fast-paths.md) and
[lazy Jarl successors](../benchmarks/training-lazy-jarl.md).

### Lighter monitoring and collection loading

- Training monitoring coalesces pending polls instead of superseding them, loads
  hardware detection and worker connectivity independently of job progress,
  requests compact job summaries, and fetches full history and the bounded log tail
  only for the selected job. Obsolete detail requests are cancelled, newer summary
  progress is preserved over an older detail response, and a failed poll recovers
  instead of freezing the dashboard. Existing clients keep the full-list default
  (PRs #43, #44 and #45).
- Backend changes reuse list snapshots, add an index for active-job lookups, group
  worker counts into one query and avoid rewriting unchanged local-job records,
  while still recovering a late terminal result once without losing retained
  history.
- The saved-tournament collection is projected inside SQLite
  (`json_remove(data, '$.result')`) instead of decoding retained match histories in
  Python, and the browser re-fetches a selected tournament's full record only when
  its status, completed game count or end time changes.

Synthetic API measurements against `0.33.0` main: job navigator **1.202 s → 26.4 ms**
and **7.99 MB → 24.6 KB** per response; worker list **580 ms → 4.5 ms**. Tournament
collection: decoded JSON **20.4 MiB → 14 KiB** and SQLite reads **25 → 1** per
listing, median collection time **0.753 s → 0.178 s**, and 600 polls of one selected
tournament **266.4 MB → 11.7 MB**. A single poll of a running tournament decodes
**850 KB → 572 B**. See
[monitoring responsiveness](../benchmarks/training-monitoring-responsiveness.md)
and [tournament collection loading](../PERFORMANCE.md#tournament-collection-loading).

### Monitoring and tuning overhead

- The training loop's instrumentation is one aggregated counter update per searched
  position and per optimizer batch (measured 0.65 µs per call, well below 0.1% of a
  normal run), and heartbeats write a bounded file (294 B, 0.13 ms) instead of the
  retained snapshot (120 KB, 9.1 ms).
- A tuning study no longer re-reads its whole Optuna study after every trial: the
  completed-trial counter follows Optuna's own trial callback and the history is
  read once at load and once at the final aggregation. For a 1,000-trial study that
  is 2,000 stored trials touched instead of 500,500. The count never includes a
  pruned, cancelled or failed trial.
- A remote worker forwards the bounded projection while the child revision is
  unchanged, cutting reporting for a 2,000-iteration job from 6.2 MB per minute to
  13 KB per minute; the retained row write is deliberately unchanged because it
  still carries the dashboard history, the lease and the report sequence.

See [monitoring overhead](../benchmarks/training-monitoring-heartbeat.md),
[tuning bookkeeping](../benchmarks/tuning-bookkeeping.md) and
[remote monitoring](../benchmarks/training-monitoring-remote.md).

## Interface and API changes

- The workshop names the exact training field a rejected configuration failed on,
  for a top-level and a nested tuning field (`training.<field>`), marks the matching
  input and keeps every entered value so one field can be corrected instead of the
  whole form being rebuilt. `output_dir` and `registry_dir` remain CLI-only inputs:
  the API refuses them by name with an explanation, because a client must not choose
  a server path, and importing a shipped `configs/*.json` in the workshop reports
  them as ignored. `frontend/src/trainingContract.json` is the single accepted
  vocabulary, and both test suites assert it.
- `GET /api/tournaments` now returns lightweight summaries by default and accepts an
  explicit `?summary=true`; `?summary=false` returns the complete records including
  match histories and is intended for tooling rather than polling. Exports always
  contain the complete saved data.
- The live training header shows the job elapsed time, the current iteration
  duration and the current phase duration, with the heartbeat state and phase
  counters. The overview's **Iteration** KPI keeps the last completed iteration used
  by checkpointing and resume. A tuning job shows the study duration in the header,
  the active trial's duration and the trial's own timers; a historical tuning job
  without a study-level duration shows no job elapsed time rather than presenting
  one trial's time as the whole job's.
- Fixed-role comparisons carry a **Fixed-role comparison** label in the saved
  collection and label their seats **Attackers** and **Defenders**.
- Monitoring payloads are additive: fields a client does not know are ignored, and
  a legacy client's full-list request still works.

## Upgrade and installation

1. Stop/cancel active training and tournaments and pause remote claim loops. Take a
   complete stopped-writer backup of the data root and protected configuration,
   retaining matching `0.33.0` code.
2. After `0.34.0` is published as a stable release with its verified archive digest,
   use the production updater:

   ```sh
   hnefatafl-update --check
   hnefatafl-backup
   hnefatafl-update --version 0.34.0
   ```

   On a Proxmox host, prefix these commands with `pct exec <CTID> --`. Fresh
   installations follow [Deployment](../DEPLOYMENT.md). A branch, tag or GitHub
   automatic source archive is not a production installation asset.
3. Confirm schema **13** and application readiness. This release adds **no database
   migration**: tournaments, training jobs and accounts keep their existing tables
   and records. A tournament without an explicit `mode` remains a balanced round
   robin, and an existing job progress file without the new monitoring fields simply
   omits them.
4. Update remote workers to **0.34.0** before assigning new work. The evaluation
   fields are capability-negotiated: a legacy worker keeps sequential evaluation and
   never receives the new keys, while an explicit `batched` or `training` selection
   requires an updated worker. Live monitoring is backward compatible: an older
   worker's snapshot is displayed without a heartbeat state, phase timer or phase
   counters instead of inventing values.
5. Optional new settings: `evaluation_mode`, `evaluation_concurrency`,
   `evaluation_batch_size` and `evaluation_inference_backend`. `auto` batches CUDA
   and keeps PyTorch CPU/MPS sequential, so CPU training behaviour is unchanged.
   Review the queue-wait caveat before setting a binding evaluation deadline.

No model or checkpoint format changed (tensor format 1), and no runtime
configuration key was removed or renamed. Schema-13 code from `0.33.0` remains
compatible, so a rollback needs no reverse migration.

## Limitations

- Heartbeat states are advisory, and their thresholds (two minutes for a long
  operation, ten minutes for a potentially stalled one, twenty seconds without
  publication) are fixed in the frontend rather than configurable per job. A
  hard-killed worker leaves its last heartbeat on disk; the server still determines
  the terminal state from the process, result file or lease.
- `phase_progress` is a live estimate that counts searched positions and games
  started, not unique replay positions, and it is cleared on every phase change.
  Initialization stages report phase and elapsed time only, because no unit counter
  exists before the first self-play game. A study's retained snapshot keeps the last
  trial's data but not its live stage, timers or counters.
- Monitoring performance was measured as protocol, serialization and synthetic-API
  cost. No network, TLS, remote CPU or GPU was exercised, so real-world remote
  throughput is not established, and CUDA training throughput recovery is
  unverified.
- GPU numbers come from one RTX 3060 host (CUDA 12.6, float32). Batched evaluation's
  Champion runs produced different work hashes from sequential, so equivalent
  Champion outcomes, scores and promotion decisions are **not** established; treat
  that comparison as unresolved. A 50-iteration run without CUDA stalls is a
  stability observation, not a benchmark, and it does not generalize to other CUDA
  runtimes.
- Batched evaluation and the engine/search fast paths are throughput and
  work-avoidance changes. No playing-strength or model-quality improvement is
  claimed, and no new pretrained model is included.
- Fixed-role results are side-specific by construction and are not a balanced
  overall-strength comparison. The frontend keeps no tournament detail cache, so
  switching back to a previously viewed tournament re-fetches it, and no
  incremental or paginated match-history endpoint was added.
- Headless neural opponents still need a resolvable `model_path`; a `model_id` is
  never turned into a filesystem path.
- Browser coverage uses Chromium and phone emulation; physical Safari and
  classic-scrollbar desktops were not established by these runs. CUDA and Intel
  OpenVINO GPU execution remain unverified where hardware is unavailable.
