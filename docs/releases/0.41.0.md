# 0.41.0 - Arena v2, player tournaments, automatic progression and public spectators

This stable milestone turns the Arena v2 program into delivered player-facing
surfaces: a four-theme responsive Arena, persisted same-device Local 1v1,
human double-elimination tournaments with durable server settlement, earnable
portraits with automatic tiered achievements, and signed-out public live viewing
and replay. It also adds rating history and rated streaks, a unified Play and
record-discovery experience, a consolidated Workshop, substantial frontend
loading and polling reductions, and fail-closed dependency auditing. It includes
every change merged to `main` since published `0.40.0`: 30 pull requests,
[#73](https://github.com/freeDom-/hnefatafl/pull/73) through
[#95](https://github.com/freeDom-/hnefatafl/pull/95),
[#97](https://github.com/freeDom-/hnefatafl/pull/97) and
[#100](https://github.com/freeDom-/hnefatafl/pull/100) through
[#105](https://github.com/freeDom-/hnefatafl/pull/105), including their review
fixes.

**Compatibility:** the online database schema advances from **15** to **21**;
the account schema remains **9**, checkpoint tensor format **1** and job-archive
schema **3** are unchanged. No training algorithm, training configuration,
checkpoint payload or remote-worker capability is changed by this milestone.
Server and workers must still run the exact same release, so update workers to
**0.41.0**. New player-tournament clients must send an explicit `match_mode`,
and the manual achievement-confirmation endpoint is removed in favour of
automatic authoritative awards. Public online discovery is enabled by default
and can be disabled for a deployment. The upgrade is forward-only and needs a
stopped-writer backup; matching-schema restore and recovery rules are described
below. CUDA and MPS execution remain unverified in the CPU implementation
environment, and no playing-strength improvement is claimed.

Full comparison: [`0.40.0...0.41.0`](https://github.com/freeDom-/hnefatafl/compare/0.40.0...0.41.0).

## Arena interface and themes

### Four-theme responsive Arena (#75, #84)

- The authenticated application now uses one persistent Arena shell across The
  Great Hall, Battlefield, Statistics, Leaderboard, Hall of records, Player
  tournaments and the Hall of Renown. Desktop gameplay and replay keep the same
  sidebar and top bar instead of switching to the legacy horizontal header;
  tablet and phone layouts use one primary navigation at a time, with a compact
  header, bottom Arena navigation and reserved board clearance.
- Four complete themes ship with original artwork and shared material
  treatments: **The King's Table** (default), **Iron & Ash**, **Saga Hall** and
  **Classic Table**. Named themes are an additive `uiTheme` preference and own
  the shell surfaces without overriding the independent board, token, density
  and language choices. Obsolete color-mode and separate Classic-look controls
  are removed.
- Existing browser-local appearance choices migrate automatically and
  idempotently: Light becomes Classic Table, Dark becomes Iron & Ash, Wood
  becomes Saga Hall, and a missing, invalid or follow-device value becomes The
  King's Table. A valid named theme wins over an obsolete mode; first paint uses
  the same catalog as React without an extra runtime request.
- Interface scale is explicit once chosen. With no saved scale, CSS viewports at
  least 3000 px wide and 1600 px tall select Large; other viewports use Default,
  so full 1080p uses Default and full 4K uses Large. Zoom and OS scaling change
  CSS space rather than being guessed from physical monitors.
- Artwork is local and account-independent: carved raven-pillared Saga Hall and
  stone/forged-metal Iron & Ash scenes, scalable bronze/carved SVG framing, and
  responsive fallbacks. Decorative scenes contain no board, labels or controls.
  Reduced-motion preferences are respected, and the corrected
  email-verification warning meets normal-text contrast in all four themes.
- Visual acceptance covers empty and populated Great Hall, Battlefield, active
  single-player, local, online, replay, Statistics, authorized Workshop and
  appearance settings at 1920×1080 and 3840×2160, plus Chromium 200% zoom.
  Committed screenshots and contact sheets are linked from the
  [design-system guide](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/DESIGN_SYSTEM.md).

### Norse terminology and consistent navigation (#101, #103)

- User-facing destination names now use the approved Norse terminology:
  **The Great Hall** (Dashboard), **Battlefield** (Play), **Trials of Valor**
  (competition), **Hall of Renown** (Portrait Hall), **Call to Battle**
  (games awaiting you), **Recent Battles** and **Deeds of Valor**. German
  translations accompany every rename.
- The desktop sidebar's archive entry is now **Hall of records**, matching the
  page heading and tablet navigation; compact mobile navigation keeps
  **Replays** / **Wiederholungen**.
- Routes, navigation destination IDs, CSS classes, API paths, database fields,
  portrait IDs, unlocks and selections are unchanged. Functional labels such as
  Play again, Replays & Analysis actions and the AI Workshop remain intact.

## Play, replays and Local 1v1

### Three Play modes and one resume path (#74, #81)

- The Great Hall and Battlefield share three equal-start creation modes:
  **Play online**, **Local 1v1** and **Play vs AI**. Only online creation
  requires a verified account; Local 1v1 and vs-AI games are never rated.
- Local 1v1 is persisted same-device pass-and-play for the signed-in account.
  Two clearly labelled human seats reuse the shared engine, rulesets,
  authoritative move validation, undo/redo/seek/restart and optimistic version
  guards. No AI opponent, background search or move advisor runs, and no online
  match, clock, matchmaking entry, rating event or Elo change is created.
- Local games live in a distinct `local` category (schema 16) and are excluded
  from `/api/games`, `/api/stats` and single-player/vs-AI statistics. Owners can
  list and replay them through the personal routes; trusted all-data
  administrators can read them through the Hall. Only the creating account may
  mutate them. Seat labels reject control characters, embedded newlines and
  bidi controls.
- Battlefield resumes the remembered running game with a history replacement,
  so Browser Back no longer reopens Play and immediately resumes the same game.
  Delayed resume responses cannot override a newer navigation choice. Common
  "Your turn / Continue" ordering distinguishes authoritative online turns from
  local games where both seats are human.

### Unified record discovery (#81, #83, #103)

- The authenticated online lobby keeps All games / My games / My turn, bounded
  server pagination and a server-side ruleset filter. It lists live games and
  links completed records to the Hall of records instead of mixing live and
  archived play.
- The Hall supports a **Record scope** selection for all records, online
  multiplayer, singleplayer and Local 1v1. Nonterminal online records are marked
  **Live** and open the live board; completed records open the read-only replay.
  Local records replay through the owner-only route with no analysis surface.
  Only completed online games and single-player records expose the analysis tab.
- Lifecycle filters are category-aware. Ordinary accounts can filter their own
  single-player and local records as in progress or completed, while the online
  scope keeps waiting/active/completed/cancelled/voided states. A bookmarked or
  direct URL with an incompatible category/status pair is canonicalized and its
  cursor cleared, so an invisible filter cannot remain active while other
  filters and deep links survive. Browser Back never revisits the invalid
  intermediate state.
- Completed online-game analysis now keys moves, stored analytics and advisor
  state by the real online game ID instead of a participant account ID. This
  restores full move history and analysis at the terminal position (#77).

## Player tournaments

- Human competition has its own `/api/player-tournaments/*` namespace and
  `/player-tournaments` Arena route, separate from the Workshop's AI
  tournaments. Schema 18 adds tournament, entrant, match, leg and append-only
  audit tables; later schemas add durable settlement and scheduling state. The AI
  `/api/tournaments/*` namespace and its `tournaments` table are untouched.
- **Double elimination** is enforced by two match losses, not two lost legs.
  Non-power-of-two fields use recursive seeding with propagating byes. The lower
  bracket alternates drop and consolidation rounds, and a lower-bracket
  grand-final win forces a bracket-reset match. No random winner is generated:
  unresolved matches use the higher seed, the undefeated upper finalist in a
  drawn grand final, or an explicit administrator override.
- New matches use two side-swapped real casual online games in either
  **sequential** (form default) or **simultaneous** mode, each with its own clock
  allocation and optional total-clock increment; advancement waits for both
  results. Historical `single` and 1–5-leg tournaments retain their stored modes,
  results and execution behavior. Tournament legs never write rating events or
  rated achievement credit.
- Match identities are deterministic and settlement is idempotent. A corrected
  or voided result marks the affected match disputed and stops advancement;
  administrators can rebuild the bracket from authoritative games or override a
  ready match, with voided outstanding games and bounded audit entries. All
  moderation is permission-checked, version-guarded and audited.
- Registration, withdrawal, discovery, details, source-connected upper/lower
  bracket and accessible list alternatives use server authority and expose only
  published participant fields. Creators see start controls when policy permits;
  administrators retain moderation controls. Active verified accounts are
  limited to three active tournaments and five per rolling 24-hour window.
- Full tournaments start at their scheduled UTC instant through a persistent
  server worker, without a browser. An unfilled tournament with at least two
  eligible entrants may start early by its creator; administrators can override.
  Overdue scheduled registrations are queued on upgrade, starts are retried
  durably, and an active bootstrapped administrator may manage tournaments
  before email verification while ordinary users still require it.
- The compact calendar keeps focus inside the dialog, escapes the scrolling
  container through the native top layer, fits the visual viewport and preserves
  date/time segments and caret position while editing, including partial and
  pasted input. The route and calendar load lazily on navigation.
- Durable server settlement runs without a browser. Committed bracket work is
  resumed after restart, terminal result revisions are reconciled once at
  startup, retries use a persisted queue, and a cancelled tournament retires all
  outstanding legs through the online core in the same transaction. See
  [player tournaments](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/PLAYER_TOURNAMENTS.md)
  and the
  [scheduling validation](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/validation/player-tournament-scheduling.md).

## Public spectator arena

- Signed-out visitors can browse `/watch`, open a live online game and inspect a
  completed read-only replay, including direct `/watch/games/{id}` and
  `/watch/games/{id}/replay` links. The public layout is complete in a production
  build and independent of the authenticated application bundle.
- Public discovery is read-only and online-only. It supports ruleset, status,
  effective-outcome and public-player filters, literal Unicode-aware player
  search, opaque keyset paging and bounded limits. There are no join, move,
  concede, void or analysis routes under the public namespace. Single-player and
  local records never appear.
- Live and waiting games expose only the current position, captured counts,
  participants, clocks and status. They never expose moves, evaluations, hints,
  best moves or win chances. Completed games add validated move history and the
  effective result; a void is published as no winner and unrated.
- Completed replay may show only analysis that is already stored for the
  terminal position. A public request never runs inference, writes analysis or
  reserves identity runes. Stored reports are projected through a fixed
  allowlist and type checks, so model paths, seeds, runes, search diagnostics and
  other private fields cannot leak.
- Public participants expose canonical public names, the server-resolved
  published portrait ID and public ratings only. Emails, account/session
  identifiers, private profile fields, birth dates, private notes and withheld
  display names are excluded. Unknown games and live games requested as replay
  return `404`; malformed identifiers fail validation with `422`.
- The namespace is gated by `HNEFATAFL_PUBLIC_ONLINE_ENABLED` (default enabled)
  and has a per-IP sliding-window limit of 60 requests per 60 seconds. Completed
  detail/replay responses are publicly cacheable for 60 seconds; live and index
  responses remain `no-store`. Other API responses are forced `no-store`.
- The production Watch Hall fixed a stylesheet-loading regression where public
  JavaScript executed without its CSS and authenticated assets were preloaded
  unnecessarily. Public JS/CSS request bytes fell from 1,219,722 to 549,340
  uncompressed (about 55%), or from 353,878 to 168,431 offline-gzip bytes. See
  [public online](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/PUBLIC_ONLINE.md)
  and
  [production validation](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/validation/public-watch-production.md).

## Progression, portraits and achievements

### Earnable portraits and the Hall of Renown (#78, #86, #101)

- Twelve stable portrait IDs provide the always-available **Shieldbearer**
  default plus victory, side, ruleset and rated-streak unlocks. The Hall of
  Renown presents locked, ready and permanently entitled portraits, server-owned
  progress, selection and accessible unlock notices. The profile and Great Hall
  link to the gallery, and published portrait IDs appear in leaderboard and
  online participant projections without exposing private achievement progress.
- Portrait selection is explicit and account-scoped. Unknown or retired IDs are
  rejected; a locked portrait is not selectable; repeating a selection is
  idempotent. A retired selection falls back to the always-available default,
  while grandfathered entitlements remain usable. The local asset allowlist
  accepts no account-supplied path, and failed artwork keeps a sized, centred
  fallback on every route.
- Artwork uses optimized 1024×1024 gallery redraws guided by the earlier 320px
  originals, loaded lazily and capped at native pixel density. Smaller profile,
  leaderboard, dashboard and player-card contexts keep the original assets. The
  gallery assets total about 2.7 MiB; original high-resolution sources were not
  available. See
  [portrait artwork](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/PORTRAIT_ARTWORK.md).

### Automatic tiered achievements (#94)

- Achievement catalog **3** and portrait catalog **2** define **77 milestones
  worth 6,290 points** across rated wins, per-ruleset wins, attacker/defender
  wins, human-versus-AI wins, successfully analyzed replays, best rated streaks
  and completing a Local 1v1 game. Thresholds, incremental point schedules and
  legacy milestone IDs remain stable.
- One idempotent award service runs inside the authoritative rating-ledger,
  local/AI completion and successful-analysis transactions. Unique append-only
  awards and entitlements survive retries, corrections, voids, pool rebuilds and
  concurrent requests. A result withdrawn before its award never grants it;
  later corrections never delete a reward already earned.
- Schema **21** seeds the updated catalogs and performs one controlled,
  idempotent reconciliation of existing authoritative records during the
  migration transaction. Existing portrait entitlements and selections are
  grandfathered; new grants use the current requirements. Reopening an upgraded
  installation does not repeat the reconciliation, although a large history can
  lengthen the one-time upgrade.
- The Hall shows permanent earned tiers, current recorded progress, the next
  unawarded target and an overall score. A correction may lower current progress
  without lowering an earned tier. The client never supplies progress, points or
  reward amounts.
- One shared account-scoped progression read serves the authenticated shell.
  Completion, successful analysis, profile changes, focus, reconnect and
  visibility events coalesce refreshes; the Great Hall drives it from its
  existing result-totals poll, while other routes use a 15-second visible-tab
  backstop. Historical notifications are suppressed at session baseline, and
  notifications are not a durable notification history.
- Rated completion uses a bounded streak fast path: a new loss or draw skips the
  streak criterion, and a winner probes only its trailing wins to the next
  unawarded milestone, falling back to the exact ledger fold when it reaches one.
  Corrections, withdrawals, pool rebuilds and migration always fold exactly. On
  a synthetic 2,000-game ledger the measured median was 3.90 ms for the full
  fold versus 0.045 ms for the three-row probe (about 87×); this is a component
  measurement, not a whole-application latency claim. See
  [progression](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/PROGRESSION.md)
  and the
  [streak measurement](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/benchmarks/progression-streaks.md).

## Ratings, statistics and leaderboard

- Multiplayer statistics gain an authoritative **Rating history** section for
  each ruleset, built from the applied rating ledger in immutable sequence order.
  It plots only recorded `rating_after` values, marks missing legacy timestamps
  as explicit gaps and corrected results with a distinct marker, and lists the
  newest bounded page with date, result, signed change, rating and opponent.
  Current rating, per-pool and aggregate current/best rated win streaks accompany
  the chart. Empty, loading, stale/retry and "most recent 100" states are
  explicit (#76, #79).
- A new **Local 1v1** statistics tab reports account-wide games, completed and
  in-progress totals, attacker/defender wins and draws with average length. It is
  deliberately non-Elo and hides the per-ruleset selector because the owner
  endpoint returns account-wide totals (#79).
- The full leaderboard adds ruleset selection, rank, Elo, rated games, provisional
  status, page count and published country/city/age columns. An always-available
  **Your rank** summary keeps the signed-in standing readable off-page, explains
  the provisional threshold and clamps safely when a shrinking pool empties the
  current page. The compact Great Hall leaderboard preserves the same policy. Elo
  initial value, K factor, pools, provisional threshold and rebuild rules are
  unchanged (#75, #79, #86).
- Published portraits and canonical public names are used consistently across
  leaderboard and online surfaces, with batched lookups rather than per-row
  requests (#86).

## Workshop and training UI

- The Workshop keeps its existing training, tuning, resume, import/export,
  model, worker and AI-tournament operations while consolidating presentation
  into shared Training/Tournaments surfaces, navigation and spacing (#92).
- The job navigator renders a bounded 20-row page and a bounded native selector
  instead of every filtered job. With 1,000 identical summaries the measured
  React/DOM tree fell from 1,000 rows, 1,001 options and 8,027 navigator
  descendants to 20 rows, 21 options and 191 descendants. This is a DOM-size
  measurement, not a frame-time, memory, server or network claim.
- Pagination preserves a valid page through poll-driven shrink/expand, follows
  explicit selection, and supports zero, one, twenty, fifty-seven and one
  thousand jobs with filters, sorting and keyboard selection. Same-hash Models
  and Workers links reopen collapsed sections, scroll and focus them. **Show
  selected job** opens the collapsed desktop disclosure and transfers focus once
  after the restored view renders, without replaying a completed focus request
  on later polling. AI-comparison and empty-state spacing use shared gap tokens
  in every theme and language.
- Training algorithms, checkpoint formats, job storage, model lifecycle and
  remote-worker protocol are unchanged by this release.

## Browser analysis research (not shipped)

- The isolated `spikes/browser_offline` harness now includes Phase 1A
  **Jarl** playback analysis and Phase 1B trained-model **ONNX export plus
  browser inference**. The browser worker validates the requested
  model identity (digest, ruleset and board size) before inference, owns
  cancellation and asset loading through one operation token, and releases
  tensors on every path. Native/browser parity covers all 39 fixture positions;
  request-identity corruption, tensor cleanup, client lifecycle and 11
  actual-browser UI checks also pass on smoke weights.
- Larger-board reference vectors were reduced to compact JSON so the Copenhagen
  fixture fits the 16 MiB limit (11.55 MB compact versus 16.96 MB indented).
  The evidence distinguishes parity from work equivalence and remains
  fixture/smoke evidence, not competitive-model or physical-device validation.
- This is research only: no production route, API, authorization, engine rule,
  training behavior, database schema, CSP, frontend CSS/component or eager
  dependency changes. Phase 2 browser neural MCTS, production integration,
  competitive weights, physical WebGPU execution and representative memory or
  playing-strength evidence are not delivered. See the
  [roadmap](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/designs/browser-analysis-roadmap.md)
  and [Phase 1 validation](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/validation/browser-analysis-phase1.md).

## Performance optimizations

- Feature modules for New Game setup, Training, AI Tournaments, recorded review,
  analysis, online management, profile/statistics and the Workshop are deferred
  until first use. The shell and live board remain eager. Initial production
  graph budgets are JS **600,000 raw / 200,000 gzip** and CSS **150,000 raw /
  35,000 gzip**; the final measured graph was **569,155 raw / 181,828 gzip JS**
  and **114,187 raw / 23,803 gzip CSS**, down from the earlier roughly 1.0 MB JS
  baseline. This is loading-graph evidence, not a load-time or capacity claim.
- Deferred imports share one code-only loader with accessible loading, retry and
  reload states, unmount guards and paused gameplay clocks. A pending shared
  stylesheet prevents a feature from mounting before it is styled. A failed
  stylesheet shows a reload-required panel instead of mounting unstyled, while
  JavaScript/render failures keep Retry. The New Game setup hook binds every
  asynchronous load and creation to an owned generation, so navigation, account
  switches, dismissal, superseded clicks or late responses cannot reopen a
  dialog, navigate away or persist stale preferences (#93).
- Dashboard reads are reduced and suspended while the tab is hidden. Failure
  backoff is bounded, so a failing 60-second read backs off to 120 seconds while
  5/10-second reads cap at 30 seconds, and success resets the cadence.
  Permission invalidations are sequenced so a newer event survives an active
  read and coalesces into one follow-up. Achievement invalidation follows
  non-hero local and single-player completions, side-specific corrections and
  active-hero completions without adding polling (#91, #94).
- The five-context production-fixture measurement recorded 11 requests/minute
  per context when idle and visible, 23/minute with an active game, and zero
  while all contexts were hidden, with no failed reads. Five contexts shared one
  disposable account, so this is not a many-player capacity result. See
  [Dashboard polling](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/validation/dashboard-polling.md).
- A disposable real-HTTP backend read benchmark covers Great Hall reads, the
  online lobby, statistics/leaderboard, completed replays and human tournament
  discovery/brackets. Its corrected eight-account baseline completed 936/936
  requests with HTTP 200 and medians of 5.79 / 21.25 / 45.64 ms at concurrency
  1 / 4 / 8. These are short same-host loopback reads with coarse tails, not
  production capacity, WAN, TLS, proxy or physical-device evidence. The
  benchmark refuses non-disposable storage, hard links, symlinks, mount
  crossings and malformed or partial mount tables, bounds worker shutdown and
  preserves partial samples on interruption (#97, #105).
- Public listing order uses an indexed `(updated_at, id)` path and skips the
  discarded total count; public listing participants are resolved in one batch
  per page. Player-tournament match listings are batched, and the tournament
  route/calendar are split into their own lazy chunk (#82, #90).
- Learning-history, AI-search and training performance behavior from `0.40.0`
  is unchanged; this milestone's benchmarks concern frontend loading, polling,
  backend reads, progression streaks and Workshop DOM size.

## Security, reliability and bug fixes

- **Dependency audit governance (#88, #95, #100, #102).** Development Vitest is
  pinned to 4.1.12, removing the old vulnerable development-toolchain packages.
  A dedicated `security` CI job audits the committed lockfile and a
  production-only audit without installing dependencies. The validator is
  fail-closed: every vulnerable package must map to an accepted advisory;
  non-GitHub advisories, malformed reports, metadata/count mismatches, stale or
  expired exceptions, runtime findings, changed severity/range/package sets or
  changed reviewed versions fail. Approval metadata is mandatory only when an
  exception is active, and identifiers must be actual strings. The withdrawn
  picomatch advisory is removed from the active exception list; current full and
  production audits report zero vulnerabilities, with no ignore list or
  threshold reduction. CI also gained a Node 22.12 minimum-version job.
- **Public and tournament authority.** Public routes are GET-only, omit cookies
  and authorization even with a stale session cookie, expose no private category
  or active-game analysis, and never mutate or generate analysis. Tournament
  settlement, starts, moderation, corrections and rebuilds commit
  transactionally with deterministic identities and retries; cancelled legs are
  retired and disputed brackets stop advancing (#80, #82, #87, #90).
- **Completed online analysis identity (#77).** Analysis moves, stored analytics
  and advisor state now use the online game ID rather than a participant account
  ID, restoring full history and terminal-position analysis.
- **Hall lifecycle and navigation (#83, #103).** Category-aware filters, URL
  canonicalization, cursor resets and one consistent Hall of records name remove
  invisible filters and the last desktop terminology mismatch.
- **Date/time and tournament controls (#90).** Manual date/time edits preserve
  segments and caret position, separator-adjacent deletion removes one digit,
  partial/full paste and numeric-keypad entry remain predictable, and the
  calendar stays inside its dialog and visual viewport. Tournament return clocks
  start after the write lock is acquired; cancelled legs and corrections no
  longer leave playable or contradictory games.
- **Dashboard and progression freshness (#91, #94).** Bounded polling backoff,
  hidden-tab suspension, sequenced permission invalidations, remote and non-hero
  completion refreshes, side-specific corrections, partial history tolerance and
  one coalesced notification per new milestone/portrait prevent stale or
  duplicate progression state.
- **Portrait and Workshop interaction fixes (#86, #92).** A confirmed portrait
  selection stays successful when the follow-up achievements read fails, later
  authoritative refreshes recover from lost responses, account switches cannot
  show another account's selection, and direct routes keep sized fallbacks.
  Selected training-job focus is restored once without being stolen back on
  later polling.
- **Public Watch Hall reliability (#87).** Production CSS loads with public
  modules, terminal spectator messaging and long `Retry-After` waits are
  correct, action targets meet the 44px mobile touch size, and production
  geometry/asset checks run against the real FastAPI boundary.
- **Benchmark storage safety (#97, #105).** The disposable benchmark reader
  preserves literal carriage returns, fails closed on partial mount tables,
  rejects hard links, symlinks, ownership/permission inconsistencies, mount
  crossings and nested mounts, bounds worker shutdown and retains evidence when
  cleanup cannot be proven safe.

## Breaking changes and migration notes

- **Database schema 15 → 21.** The additive upgrade introduces the schema-16
  local-game category, schema-17 progression catalogs, schema-18 human tournament
  tables, schema-19 settlement outbox/planned starts, schema-20 persistent due
  starts and replay-analysis receipts, and schema-21 automatic-achievement
  reconciliation. Existing games, accounts, sessions, ratings, jobs, models,
  checkpoints and historical tournament records are not rewritten. Back up with
  stopped writers before upgrading; a large history may lengthen the one-time
  schema-21 reconciliation.
- **No downgrade.** Older code refuses the newer online schema, and automatic
  restore requires matching current schemas/columns. Deploy backend and frontend
  together, keep the matching backup and `0.40.0` code, and use the documented
  forward-repair or manual reconciliation path rather than forcing an old binary
  onto a new database.
- **Remote workers.** Server and workers must still match the exact release.
  Update workers to **0.41.0** before new assignments. Checkpoint tensor format
  **1**, job-archive schema **3**, training configuration and worker advertised
  capabilities are unchanged.
- **Player-tournament API.** New tournaments require an explicit
  `match_mode: sequential | simultaneous`; missing, null or unsupported modes and
  any supplied `match_legs` field return `422`. New tournaments always store two
  side-swapped games. Existing single and 1–5-leg records remain readable and
  executable. Browser clients of the tournament calendar receive the same lazy
  route and native date/time controls.
- **Achievements API.** The manual confirmation endpoint is removed. Awards are
  granted automatically inside authoritative transactions; GET remains
  read-only and portrait selection never grants achievements. Existing awards,
  portrait entitlements and selections are preserved, and new grants use the
  current catalog requirements. Custom clients that called the removed endpoint
  must stop calling it.
- **Public online discovery.** Public GET routes are enabled by default for
  existing deployments. Set `HNEFATAFL_PUBLIC_ONLINE_ENABLED=false` to return
  `404` from every public handler without changing authenticated routes. The
  in-process per-IP limiter assumes the documented single API worker; a
  multi-worker deployment needs a shared limiter.
- **Appearance and UI labels.** Obsolete color-mode/Classic-look preferences
  migrate to named themes as described above. Norse labels replace several
  English/German user-facing names, but routes, navigation IDs, API paths,
  schemas, field names, portrait IDs, unlocks and selections do not change.
- **Permissions and proxies.** New public, progression and player-tournament
  routes are recorded in `docs/API_PERMISSIONS.json`. Deployments or reverse
  proxies with an explicit route allowlist must include the new authenticated
  and public paths; do not expose mutation routes anonymously.

## Upgrade and installation

1. Stop or cancel training and tournaments, pause remote claim loops and
   unmanaged writers, and take a stopped-writer backup of the data root and
   protected configuration. Retain matching `0.40.0` code with that backup.
2. After stable publication and source-asset verification:

   ```sh
   hnefatafl-update --check
   hnefatafl-backup
   hnefatafl-update --version 0.41.0
   ```

   On Proxmox, prefix with `pct exec <CTID> --`. Use the attached
   `hnefatafl-0.41.0.tar.gz`, not GitHub's automatic source archive. Fresh installs
   follow [Deployment](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/DEPLOYMENT.md).
3. Deploy backend and frontend together, confirm readiness and schema **21**, and
   check existing games, local records, replays, achievements, tournaments and
   pending scheduled starts. No account, checkpoint, job-archive or training
   migration is added.
4. Update workers to **0.41.0** before new assignments. No new worker capability
   flag is required for this milestone; existing exact-version matching remains
   authoritative.
5. Decide whether public discovery should remain enabled. If it should be off,
   set `HNEFATAFL_PUBLIC_ONLINE_ENABLED=false`, restart and confirm `/watch` and
   `/api/public/online/*` return 404 while authenticated routes still work.
6. Resume writers and claim loops after readiness and compatibility checks.

## Limitations

- `0.41.0` remains a milestone preview. The [release-readiness
  checklist](https://github.com/freeDom-/hnefatafl/blob/0.41.0/docs/RELEASE_READINESS.md)
  still records no chosen public distribution license, no staging/target-host
  capacity or recovery drill and no `1.0` acceptance. A green implementation
  suite is not a public-deployment authorization.
- Leagues remain a disabled **Soon** destination. The documented league policy
  is not an implementation: there is no league queue, season accounting, league
  schema or league UI in this release.
- Browser-local classical/neural analysis remains an isolated feasibility spike,
  not a production route or default. Its neural audit lacked an ONNX exporter,
  WebGPU adapter and permissive-CSP browser inference; no browser model/runtime
  package or policy weakening ships.
- Physical Safari/WebKit and physical iOS/Android devices were not validated.
  Chromium mobile emulation and explicit CSS viewports are not physical-device
  evidence. CUDA/MPS execution remains unverified on this CPU host, and no GPU,
  throughput or playing-strength claim follows from functional tests.
- Public discovery runs under one in-process rate limiter and the documented
  single API worker. Public replay exposes only the terminal position's stored
  analysis, not a public analysis service. Spectator reads are not a capacity or
  many-player load test.
- The player-tournament UI has no anonymous/public read surface. An unfinished
  game keeps its match ready until the clock expires or an administrator
  overrides it; `rebuild` re-derives the bracket and clears earlier overrides.
  Tournament games are casual and never affect Elo or rated achievement credit.
- Achievement notifications are session-scoped rather than a durable history,
  and a remote completion on a route without its own completion poll can take up
  to the 15-second visible-tab backstop to appear. Historical analysis without a
  durable successful receipt is not retroactively inferred. Browser-local
  analysis is not eligible for achievement credit.
- The portrait gallery uses 1024px redraws because original high-resolution
  sources were unavailable; it is not a claim of native high-resolution art.
  Gallery assets are about 2.7 MiB and lazy loaded.
- Backend-read and polling figures are same-host/disposable or five-context
  measurements, not production capacity, WAN, TLS/proxy or physical-device
  numbers. Workshop DOM and progression-streak figures are component-level
  measurements, not whole-application latency. Existing Vite chunk-size and
  dependency/runtime deprecation warnings may remain even though current
  dependency audits report zero findings.
