## Milestone: Concurrent self-play and batched neural inference

Training can generate independent games concurrently and evaluate their pending
MCTS positions in shared neural-network batches. The existing sequential path
remains available on CPU and CUDA; games and tournaments keep their search behavior.

### Training execution

- Add `self_play_mode`: `auto` (default), `sequential` or `batched`. Automatic
  execution batches on CUDA and stays sequential on CPU/MPS.
- Add `self_play_concurrency` (default 16, range 1–1024) and
  `inference_batch_size` (default 32, range 1–4096). The active-game count is
  bounded by games remaining; optimization `batch_size` is independent.
- Cooperatively interleave independent game/search contexts through one shared
  model, without duplicating CUDA networks or adding inference worker processes.
  Resume a dependent simulation only after its inference result is available.
- Preserve PUCT, progressive widening, terminal handling, legal-action masking,
  visits/backups, root noise, policy targets, defender-relative values and
  truncated-game bootstrapping. Retain deterministic per-game seeds and RNGs.
- Configure the new settings in Start Training, Resume Training, JSON/CLI jobs,
  Optuna inputs and remote-worker jobs. Older configurations receive defaults;
  resumed jobs retain their checkpoint identity, optimizer/replay/RNG state,
  history and best-model tracking while accepting reviewed execution changes.

### Performance evidence

Progress/result JSON and completed-iteration history retain throughput, actual
search work, inference counts/batch sizes/latency, game outcomes and phase timings.
The workshop shows these metrics and a throughput-history table alongside the
existing loss/evaluation graphs. Optional CUDA fields report peak memory.

Wall-clock duration, accumulated process CPU activity and optional CUDA-event
activity are separate measures. Ordinary runs avoid additional CUDA events or
explicit timing synchronization inside simulations; the benchmark enables CUDA
activity timing and synchronizes scenario boundaries. These times need not sum
to iteration wall time.
Final progress/result iteration wall time includes artifact persistence; checkpoint
history retains the timing snapshot taken before its own serialization.

Run the small comparison with:

```sh
.venv/bin/python -m hnefatafl.cli benchmark
# Optional explicit budget:
.venv/bin/python -m hnefatafl.cli benchmark --config configs/train-smoke.json
```

The command compares sequential/batched execution on each available device with
shared weights, seeds and search budgets, and reports actual completed work.
Unavailable CUDA scenarios are explicitly skipped. Speedup compares modes on
the same device; batching is not assumed to improve every CPU workload.

### Validation

`make foundation check` passes: **478 backend tests**, **137 frontend unit tests**,
Ruff lint/format checks, mypy, TypeScript, Prettier and the production build.
One CUDA inference test is skipped because this host has no compatible GPU.
Coverage includes independent MCTS contexts, inference equivalence/legal masking,
exact game counts, bounded out-of-order replay buffering, initial progress,
cancellation, checkpoint history, execution-mode changes on resume and remote jobs.

A separate batched CPU CLI smoke run completes four games, performs four gradient
updates, retains 32 replay positions, saves/reloads optimizer state and registers a
model that selects a legal move after checkpoint loading.

Small CPU comparisons used four eight-ply games, four simulations per move,
seed 17, two CPU threads, float32 inference and a 300-second search deadline.
Every scenario completed 32 positions and all 128 requested simulations.

| Network | Sequential CPU | Batched CPU | Sequential / batched speedup | Forward passes | Mean batched size |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4 channels, 0 blocks (default benchmark) | 0.1931 s | 0.1966 s | 0.98× | 209 → 53 | 3.94 |
| 32 channels, 2 blocks (Brandubh network size) | 0.2775 s | 0.4268 s | 0.65× | 215 → 55 | 3.91 |

Default-case positions/second were 165.69 sequential and 162.76 batched;
simulations/second were 662.74 and 651.04; neural evaluations/second were
1,082.13 and 1,063.02. The second configuration measured 115.32/74.98 positions,
461.29/299.91 simulations and 774.82/503.76 neural evaluations per second.
Both modes evaluated the same number of positions in each comparison.

These single-run, tiny-budget measurements demonstrate fewer network calls,
**not a CPU speed improvement**. CPU `auto` therefore retains the sequential path.
The second comparison used the same command with a JSON configuration containing
`{"channels": 32, "blocks": 2}`. Both CUDA scenarios were skipped; no GPU speedup
or full-game throughput is inferred from these truncated-game measurements.

### Install, update and compatibility

Stop training/server processes and back up the complete data directory before
updating. Update remote-worker code alongside the server so workers understand
the new configuration fields and batched execution path.

```sh
make install
make build
bash scripts/start.sh
```

Storage remains **schema 7**, with the same network architecture and checkpoint
format. No data migration, model conversion or CUDA-specific dependency is
required for CPU execution. Existing checkpoints/configurations remain usable;
missing execution settings default to `auto`, 16 concurrent games and an
inference batch limit of 32. Remote workers must run the updated implementation
to execute those newly supplied settings.

This host provides CPU-only validation. CUDA/MPS execution and GPU speedups remain
unverified. The full browser end-to-end suite was not run locally, and no long
training campaign was run for this milestone. Sequential and batched modes need not be bitwise
identical; reproducibility applies within a mode under consistent conditions.
Throughput and successful smoke training establish no improvement in playing
strength or calibration of the model's estimates.
