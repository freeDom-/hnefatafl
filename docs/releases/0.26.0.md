# 0.26.0 — Exact remote worker version compatibility

Exact remote worker application compatibility, persisted administrator exceptions
and uninterrupted valid remote leases across server version changes. The stable
release and annotated tag use **0.26.0**.

## Delivered behavior

- Server and workers use installed package metadata. New remote assignments require
  exact application-version equality, matching known immutable Git revisions,
  compatible protocol and the existing device/backend/inference-cache capabilities.
  Missing or malformed application identity blocks new assignments. Matching
  major/minor versions alone are insufficient.
- Outdated workers remain registered, authenticated and visible online. No token
  rotation or re-enrollment is required. Automatic scheduling skips incompatible
  workers; explicit targets return a clear HTTP 409 mismatch error. Waiting jobs
  expose distinct capacity, hardware, application-version and protocol reasons.
- Compatibility is recomputed from the running server's identity and the latest
  heartbeat. Heartbeats, claims and override mutations share the existing job lock.
  Empty/legacy heartbeat snapshots cannot inherit previous version eligibility.
- Per-worker overrides default off, persist through restarts and require an active
  administrator session plus CSRF. Changes retain actor/time audit history.
  Overrides permit known version/commit differences; unknown versions, protocol,
  hardware, inference checks and revocation remain enforced. Disabling an
  exception blocks subsequent assignments immediately.
- The workshop distinguishes connection status from compatibility, shows both
  versions and optional commits, and uses green/red/yellow/gray compatibility
  indicators. Administrator controls warn about inconsistent training and invalid
  benchmark comparisons. Selection/resume forms disable incompatible targets and
  show exceptions. All new presentation text has English/German translations.
- Existing valid leases continue progress, artifacts and completion after server
  version changes, including multiple simultaneous jobs. Original claim retries
  remain idempotent. New claims use current eligibility. Lease ownership, expiry,
  recovery and authentication continue unchanged.
- `job.software` freezes worker/server application identity and override use when
  claimed; Details and portable job ZIPs retain it. Optional revisions use immutable
  PEP 610 Git-install metadata only; normal installations never invoke Git.

## Installation and update

Use the stable `0.26.0` release's installer-compatible `hnefatafl-0.26.0.tar.gz`
asset. The release workflow checks successful Verify CI on the exact tagged main
commit and verifies GitHub's SHA-256 digest for the packaged source. New release
notes use version filenames without a prefix; historical note paths remain intact.

No database migration or re-enrollment is required. Existing worker/job JSON gains
optional fields with safe defaults. Server/worker releases must match exactly.
Update worker source and run `uv sync --frozen --extra train`, then restart with
the same token/work directory after its current jobs finish. See
[remote compatibility and troubleshooting](../REMOTE_TRAINING.md#application-compatibility-and-upgrades)
and [deployment](../DEPLOYMENT.md). The production updater still refuses active
jobs; ordinary restarts preserve leases only within the existing timeout.

## Limitations

Version information is authenticated self-reporting, not remote code attestation.
Editable/source/wheel installations without immutable VCS metadata omit commit
identity; matching official versions still work. Unreported modifications cannot
be detected. Unknown application versions require a corrected installation/report,
even with an override. Historical jobs have no fabricated software identity;
checkpoint tensor/model formats are unchanged. Overrides are unsupported software
combinations and can produce inconsistent training or benchmark results.

CPU functional tests do not establish stronger play or acceleration. Physical
CUDA, Apple MPS, Intel GPU, mobile hardware and production systemd/Proxmox upgrade
execution are unverified on this host. The supported deployment remains one API
process with independently supervised remote training slots.
