# 0.22.0 - Secure accounts and production deployment

Browser and API access now require a persistent account. Ordinary users can play
and manage their own records; training, tournaments, model management and global
data access require an active administrator. The release also adds native Debian
13 / Proxmox LXC installation and a versioned, backup-aware deployment workflow.

## Delivered behavior

- Local initial-administrator provisioning defaults to **Odin**, with prompted
  email and confirmed masked password input. There is no default password or
  public registration. Local commands create accounts and recover access.
- Salted scrypt passwords, database-backed opaque sessions, production Secure /
  HttpOnly cookies, CSRF and same-origin checks, persistent login throttling and
  immediate role/status enforcement. Account changes revoke browser sessions.
- Explicit authorization for all **57 API method/path combinations**, default
  denial of unknown routes, account-owned games/profiles and administrator-only
  privileged operations. Scoped remote workers require an active enrolling admin.
- Responsive login/logout, permission-aware navigation, private-state clearing
  between accounts and protected requests through the shared API client.
- Dedicated non-root systemd service, external HTTPS proxy configuration, native
  Linux/LXC installers, private-repository credentials and stable-release assets.
- Digest-verified downloads, bounded extraction, locked dependency builds,
  mutation draining, full verified backups, atomic activation, authenticated
  readiness checks, interrupted-update recovery and guarded rollback.

See [security architecture](../SECURITY.md), the [API inventory](../API_PERMISSIONS.json)
and the [operator guide](../DEPLOYMENT.md) for configuration and recovery details.

## Installation, migration and update

For an existing source installation, stop the service and back up its complete
data/configuration before upgrading. Use the same persistent data directory:

```sh
git fetch origin --tags
git checkout 0.22.0
make install
make build
HNEFATAFL_DATA_DIR=/path/to/existing/data .venv/bin/python -m hnefatafl.accounts migrate
HNEFATAFL_DATA_DIR=/path/to/existing/data .venv/bin/python -m hnefatafl.accounts init-admin
```

Schema **7 → 8** is additive and transactional. Existing games, local player IDs,
JSON, runes, models, jobs and checkpoints are retained. Historical game/player
records have no invented owner and remain administrator-visible. Login accounts
are separate from local player identities. Re-enroll existing remote workers.
Configure the required HTTPS origin, allowed hosts and explicit trusted proxies
before production startup; see the [deployment guide](../DEPLOYMENT.md).

For new dedicated Debian 13 installations use `scripts/linux/install.sh`; on
Proxmox use the reviewed `scripts/proxmox/ct/hnefatafl.sh`. This release uses the
`0.22.0` tag and uploaded `hnefatafl-0.22.0.tar.gz` asset required by the
production updater. Previous preview archives are not supported production inputs.

Managed installations use `hnefatafl-update --check`, `hnefatafl-backup`,
`hnefatafl-update --version 0.22.0`, `hnefatafl-update --rollback` and
`hnefatafl-update --recover`. Active/queued training and tournaments must finish
or be explicitly cancelled before activation. Rollback preserves current account
credentials/status/roles when schemas match, clears sessions and quarantines
post-snapshot application data for manual reconciliation.

## Remaining limits

Actual Proxmox creation, Debian 13 package provisioning, target-host systemd /
reboot / external HTTPS proxy operation, private-release installation, Linux
arm64 and CUDA/MPS require separate target validation. The API service uses one
process for existing catalog/job coordination. MFA, email recovery, public
registration, per-user inference quotas and online matchmaking remain future work.
Test restoration with disposable data and complete the operator acceptance checks
before public exposure. No live production deployment was performed.
