# 0.12.0 — Remote training workers

Cloud machines can now train models through an authenticated pull API while the
server retains the queue, progress, checkpoints and models. Multiple workers or
multiple slots on one machine train independent models simultaneously.

### Train on remote CPU/GPU machines

- Enroll a named worker in the workshop and choose its parallel job capacity.
  Receive its token once; the server stores the credential hash. View reported
  hardware, online/offline status, last connection and occupied slots.
- Run `hnefatafl worker --server … --work-dir … --concurrency …` on the training
  machine, supplying `HNEFATAFL_WORKER_TOKEN` through the environment. Workers
  make outbound requests and run each job in a separate training process.
- Choose this server, any remote worker or a specific worker when starting or
  resuming training. Additional jobs queue while earlier models are training.
  Local training retains its one-job limit and runs independently of remote jobs.
- Accept GPU jobs even when the server has no GPU. Explicit CUDA/Metal jobs wait
  for matching advertised hardware; automatic device selection runs on the worker.
- Transfer inference models, full optimizer/replay checkpoints and optional
  new-best snapshots to the server. Validate tensor-only artifacts before import;
  normal gameplay then uses server-owned model copies.

### Progress and lifecycle

- Display saved progress and learning charts for every job, with independent
  selection, worker labels and automatic model refresh for unselected completions.
  English/German controls cover enrollment, execution targets and lifecycle errors.
- Send progress independently of long training moves, flush the final chart data
  and retain bounded log tails. Progress and queue state survive page/server reloads.
- Cancel waiting jobs immediately or request a graceful stop for active jobs.
  Revoke a worker without disturbing unrelated workers.
- Use scoped leases, ordered reports and idempotent claims/completion requests
  to handle retries. Lost leases reject late results and stop the client process;
  explicitly resume an uploaded checkpoint to continue rather than duplicating work.
- Copy a resume input into its new job before queueing, so deleting source
  training data cannot break a waiting resume. Resume can change execution target.
- Keep credentials out of URLs, process arguments, child training environments
  and browser storage. Use private ledgers and owned worker directories for
  restart recovery; do not forward bearer tokens through redirects.

### Validation

- **355 backend tests**, **88 frontend unit tests** and **28 real-API browser
  checks pass**. Four duplicate mobile worker checks remain intentionally skipped.
  Ruff/Prettier, mypy, TypeScript and the production build pass.
- Verify worker token hashes/scoping, idempotent concurrent claims, expiry and
  revocation, queued cancellation, ordered reports, artifact limits/corruption,
  canonical completion retries and independent resume inputs.
- Inspect compiled desktop/mobile and German worker/progress views without
  overflow or browser errors. One-time credentials stay masked and out of browser
  storage. Terminal metrics use the authoritative job status.
- Startup serves v0.12.0/schema 6 while preserving all seven existing games,
  four model entries and eight rune assignments against a full pre-upgrade backup.

See [validation details](https://github.com/freeDom-/hnefatafl/blob/v0.12.0/docs/VALIDATION.md).

The real HTTP integration runs two CPU training jobs concurrently through one
two-slot worker, verifies optimizer updates, transfers full checkpoints and models,
resumes one job, then plays a legal server-side neural move after removing the
worker's local files. Desktop/mobile workshop checks verify independent charts,
queue cancellation and persistence. GPU capability selection is tested as protocol
data; CUDA/MPS hardware execution is not claimed.

### Setup, update and compatibility

Read [REMOTE_TRAINING.md](https://github.com/freeDom-/hnefatafl/blob/v0.12.0/docs/REMOTE_TRAINING.md)
for enrollment, CLI commands, GPU installation, API details and network access.
A Linux worker service template is included for adaptation on the target host.

Stop the server and back up the **complete data directory** before updating:

```sh
make install
make build
bash scripts/start.sh
```

Startup additively upgrades **schema 5 to schema 6** with the remote-worker table.
Existing game JSON, model IDs and checkpoint formats remain unchanged. Keep one
API process. Rollback to older code requires the pre-upgrade backup. Worker
protocol version is 1; use the same application release on server and worker.

Worker credentials protect `/api/worker/` routes. Keep enrollment, the browser and
other administrative APIs private or behind proxy authentication; this release
does not add application-wide accounts. Use private networking/VPN or HTTPS with
appropriate route restrictions. Remote Optuna is not supported; tuning stays local.
Slots share visible devices and do not automatically distribute one model across
GPUs/machines. Artifacts are limited to 128 MiB. The locked default uses CPU PyTorch;
install a matching official GPU build on accelerator workers.
