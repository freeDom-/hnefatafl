# 0.40.0 - Persistent Champion adaptation, selectable learning metrics and configurable analytics budgets

This stable milestone makes Champion promotion a persistent HyperController
transition, turns the Learning dashboard into one selectable-metric chart with
portable parameter provenance, and exposes a configurable neural analytics MCTS
budget with shared, retry-aware analysis coordination. It includes every change
merged to `main` since published `0.39.0`:
[#69](https://github.com/freeDom-/hnefatafl/pull/69),
[#70](https://github.com/freeDom-/hnefatafl/pull/70) and
[#71](https://github.com/freeDom-/hnefatafl/pull/71), including their review fixes.

**Compatibility:** database schema **15**, checkpoint tensor format **1** and
job-archive schema **3** are unchanged. The HyperController state schema advances
from **4** to **7**; versions 1–6 migrate as described below, and workers must
advertise the new adaptation capabilities. New optional training-parameter
provenance is carried inside existing checkpoint/history/archive containers
without a database, tensor or worker-protocol version change. Update workers to
**0.40.0** for the existing exact-version policy. CUDA and MPS execution remain
unverified in the CPU implementation environment, and no playing-strength
improvement is established.

Full comparison: [`0.39.0...0.40.0`](https://github.com/freeDom-/hnefatafl/compare/0.39.0...0.40.0).

## Training and AI changes

### Persistent Champion-aware HyperController (#70)

- A Champion promotion is now an **idempotent transition**, not a reset. The
  learned predictors, reward/action history, lifetime counters, dwell timers,
  effective learning rate and RNG survive; only the new Champion's per-Champion
  evaluation block (identity, promotion iteration, baseline, calibration offset
  and uncertainty) is refreshed. The optimizer, its moments, the model weights
  and the replay buffer are untouched.
- Champion reward is genuine **within-Champion improvement**
  `clamp(score - baseline_score, -1, 1)` against the observed baseline, so two
  identical scores yield exactly zero. The regularized baseline uncertainty is
  kept separate and only widens the decision margin; a neutral-score prior can no
  longer manufacture progress. Fixed opponents keep the historical absolute-score
  reward and its compatible predictors.
- Champion predictor updates are weighted by completed games, and a different
  candidate is adopted only when its predicted improvement exceeds the current
  rate's by a confidence margin (one standard error of the Champion's mean
  improvement). **Every** automatic Champion rate change, exploitation included,
  needs two comparable post-baseline observations. Untried candidate/context
  pairs are still explored, under a separate cooldown and preferring the
  multiplicatively nearest candidate (log-rate distance) so the rate never
  oscillates or jumps between extremes.
- New `adaptation_min_dwell_iterations` (integer **0–1,000,000**, default **0**)
  keeps a chosen rate for a minimum number of iterations in addition to the
  evaluation dwell. Both dwell timers survive a Champion promotion. A legacy
  change with no iteration metadata starts the conservative iteration dwell at
  resume.
- The controller state schema is now **version 7**. Migration is chosen from the
  schema version, not a label:

  | Version | Reward definition | Resume into a Champion (v7) |
  | --- | --- | --- |
  | 1–4 | absolute score | discard predictors (`reward_semantics_changed`) |
  | 5 | improvement vs the raw baseline | **compatible**, preserve |
  | 6 | improvement vs a shrunk baseline | discard predictors |
  | 7 | improvement vs the observed baseline | preserve |

  A version-6 fixed-opponent state stays compatible (its reward was absolute).
  Compatible predictors, the effective rate, optimizer moments, replay buffer,
  lifetime counters, dwell references and RNG survive; only incompatible
  predictors are discarded.
- Restored state now rejects cross-field inconsistencies:
  `last_exploration_observation > observations`, a positive improvement count
  without a baseline, `score_se_sum_sq` above its mathematical bound, and an
  uncertainty that disagrees with `sqrt(baseline_se^2 + score_se_sum_sq / count^2)`.
  A rejected state recovers to a clean controller with an explicit
  `unreadable_state` reason and can keep training and checkpointing without
  corrupting the model or optimizer.
- Workers advertise `hyper_adaptation_champion_transition` and
  `hyper_adaptation_state_versions`; a resumed adapted job is only offered to a
  worker whose advertised list includes the checkpoint's controller schema
  version, so an older worker cannot silently discard learned state through its
  own migration. A worker that advertises no list is assumed to understand only
  versions 1–4. `hyper_adaptation_iteration_dwell` gates a nonzero
  `adaptation_min_dwell_iterations`, while the inert zero default is omitted from
  a worker that lacks the capability. Administrator version overrides cannot
  bypass these gates.
- Monitoring exposes the active Champion identity, current-regime observations,
  lifetime warm-up, iterations since the last rate change, lifetime transitions
  (`promotion_resets` remains an alias) and the rate preserved at the last
  promotion. The Learning view and decision log mark a transition with the
  preserved rate as both used and selected.

See [online adaptation](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/TRAINING.md#online-learning-rate-adaptation),
[remote worker capabilities](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/REMOTE_TRAINING.md)
and the [controller design record](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/designs/online-hyperparameter-adaptation.md).

### Selectable learning metrics and portable parameter history (#69)

- **Learning** now offers one selectable **Learning metric** chart. The default
  **Loss by iteration** keeps both policy and value loss; policy and value loss
  can also be selected separately. Further options include replay
  occupancy/capacity, per-iteration optimizer updates, used and selected base
  learning rates, recorded training exposures, and eleven configured training
  hyperparameters.
- The selection survives progress polling and resets to the loss default when a
  different job is selected. Chart title, series, units, legend, accessible
  description and exact-value tooltips all follow the selected metric. The
  existing iteration windows apply to every metric, and the single lazily opened
  **View graph data** table adds the selected metric's exact values. Genuine zero,
  constant positive values and zero-only series remain readable; loss, evaluation
  and performance scales are unchanged.
- Each training execution records a sparse, whitelisted numeric
  `training_parameters: {version: 1, ...}` snapshot at its first completed
  iteration and whenever effective settings change. Rows reference their
  applicable snapshot with `training_parameters_iteration`. Older-worker rows
  cannot inherit stale settings, and the selected job's current configuration is
  never projected back onto unknown historical rows. Snapshots come from the
  normalized trainer settings after optimizer restoration; used and selected
  learning rates remain separate per-iteration observations.
- The optional provenance travels inside full checkpoints, `progress.json`,
  `result.json`, remote history chunks and TAR.GZ archives. Unsupported versions
  and malformed snapshots become unknown boundaries on resume; older checkpoints
  remain loadable and resumable without these fields, and source checkpoint bytes
  are never rewritten.
- Optimizer updates use the recorded per-iteration `updates` count, falling back
  to the legacy top-level `optimizer_updates` alias only when `updates` is absent
  or invalid. Valid nonnegative safe integers win, **including zero**; missing or
  invalid counts stay unknown. Cumulative diagnostics such as Schedule-Free
  `completed_steps`, adjacent-count differences and configuration never fill
  missing observations. The KPI, availability, chart and table share this
  normalization without modifying imported rows.
- Very small learning rates and weight decay use adaptive positive scaling and
  locale-aware scientific notation, so changes such as `0.000001` to `0.000002`
  remain visible with the axis still starting at zero.
- On desktop, only the job rows scroll within a viewport-relative maximum height;
  search, status, sorting and the job count stay above them, polling preserves the
  scroll position, and the mobile selector is unchanged. English/German labels
  and help accompany the new controls.

See [training dashboard metrics](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/TRAINING_DASHBOARD.md#selecting-learning-metrics)
and [historical training parameters](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/TRAINING_DATA.md#historical-training-parameters).

## Analysis and gameplay improvements

### Configurable neural analytics MCTS iterations (#71)

- Neural game analytics expose **MCTS Iterations**, defaulting to **1024** and
  accepting integers from **1 to 5000**. The per-position budget is saved in
  `advisor.config.iterations` and survives search-time edits, replay and reload.
  Higher budgets generally allow stronger search but take longer; the search-time
  limit can stop a search before it completes all simulations. Policy-only and
  neural alpha-beta advisors do not expose the control, and playing agents,
  training, evaluation and tournament budgets keep their own defaults.
- The input saves a valid value after 600 ms without typing, or immediately on an
  ordinary blur or Enter. It checks the actual focus destination and discards its
  draft and cancels its timer when focus moves to an advisor, custom algorithm or
  model selector, so rapidly typing a budget and switching advisors produces one
  settings revision instead of writing the old model's draft. Invalid drafts are
  never persisted. This fixes the previously reproduced old-model `4096` PUT
  followed by the new advisor PUT.
- Temporary HTTP 503 responses retain available partial estimates with a
  capacity-waiting status. The typed `ApiError` carries `Retry-After` guidance;
  analytics retries back off from 1 to 30 seconds, honor `Retry-After` within
  those bounds, and return to normal polling after success. Only one poll is
  active; game, position, settings and component changes abort the old request and
  its retry timer. Other errors keep manual retry.

### Shared and bounded advisor analysis (#71)

- Synchronous and background advisor clients share one running task or completed
  result per game/position/role/revision. Two analysis workers admit at most 16
  running/queued tasks; at most eight synchronous callers wait concurrently, and
  a synchronous wait is limited to 20 seconds. Overflow and timeouts return HTTP
  503 with `Retry-After: 1`, leaving request workers available for gameplay.
- Cached advice stays readable at the waiter limit. A caller timeout or
  disconnect does not cancel shared work, and once an advisor report completes,
  storage rejects replacement by late progress or another completion for the same
  position/revision. Historical synchronous replay remains read-only; explicit
  historical background analysis records a separate advisor opinion, and
  completed reports remain immutable.

See [game analysis](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/ANALYSIS.md).

## Performance optimizations

- Learning history reuses normalized rows and builds parameter columns once per
  sparse snapshot. Stepped parameter paths keep every actual transition and gap
  while omitting redundant commands along constant stretches, and configured-metric
  availability is answered from sparse snapshot rows. The committed
  [production-browser measurements](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/benchmarks/learning-metrics.md)
  cover 1,500–100,000 rows and a 100,000-row legacy history with only its final
  250 parameter rows recorded. At 100,000 rows, initial commit improved from
  **469 ms to 298.6 ms**, append-one from **384.1 ms to 255.5 ms**, parameter
  reconstruction from **143.4 ms to 76.8 ms**, and total UI heap from
  **60.8 MiB to 39.5 MiB** (post-GC JavaScript overhead above the raw input, not
  peak/RSS). Gains are not uniform: the full two-loss switch was slower in the
  sampled run. These synthetic component-level measurements exclude API/database
  work, transfer/JSON parsing and mobile hardware, and are not CI thresholds or a
  whole-application latency claim.

## Bug fixes

- Champion reward, migration and validation semantics: the obsolete shrunken
  `effective_baseline` field is removed, identical scores yield exactly zero
  improvement, and invalid restored state recovers cleanly instead of suppressing
  exploration or corrupting training (#70).
- Neural analytics no longer saves an old model's pending MCTS draft when the
  advisor, algorithm or model selector changes; the draft is discarded and its
  timer cancelled before the selector's own settings write (#71).
- Busy analytics recover from temporary 503 responses with bounded retry instead
  of failing, and MCTS iteration edits are debounced to a single settings write
  (#71).
- Legacy learning histories regain their per-iteration optimizer-update option and
  values by reading the `optimizer_updates` alias only when the modern `updates`
  field is absent or invalid, including explicit zero (#69).

## Benchmark evidence and hardware compatibility

The committed synthetic
[Champion-adaptation benchmark](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/benchmarks/champion-adaptation.md)
compares a fixed rate, a forced-reset ablation and the persistent transition on a
deterministic stream whose true best rate alternates every 20 evaluations
(5 seeds, 400 evaluations, 4 completed games each). The persistent transition
changes the rate about **nine times less often** than the forced-reset ablation
and keeps the full bounded reward history and event log instead of losing them at
every promotion. Its synthetic regret is slightly above the fixed rate because the
corrected reward removes the spurious absolute-level signal the shrunken baseline
leaked in. **This is not a strength claim and no matched-strength evaluation was
run.**

CUDA/MPS hardware was absent. The existing hardware-gated tests remain the
execution evidence boundary; no GPU memory, throughput or strength result is
claimed.

## Upgrade and installation

1. Stop/cancel training and tournaments, pause remote claim loops and unmanaged
   writers, and take a stopped-writer backup of the data root and protected
   configuration. Retain matching `0.39.0` code with that backup.
2. After stable publication and source-asset verification:

   ```sh
   hnefatafl-update --check
   hnefatafl-backup
   hnefatafl-update --version 0.40.0
   ```

   On Proxmox, prefix with `pct exec <CTID> --`. Use the attached
   `hnefatafl-0.40.0.tar.gz`, not GitHub's automatic source archive. Fresh installs
   follow [Deployment](https://github.com/freeDom-/hnefatafl/blob/0.40.0/docs/DEPLOYMENT.md).
3. Deploy backend and frontend together, confirm readiness and schema **15**, and
   check existing jobs, tournaments and replays. No database migration is added;
   checkpoint tensor format **1** and job-archive schema **3** remain unchanged.
4. Update workers to **0.40.0** before new assignments. A resumed adapted job is
   gated on the worker's advertised controller schema versions; workers that
   advertise no list are treated as versions 1–4 only. A nonzero
   `adaptation_min_dwell_iterations` additionally requires
   `hyper_adaptation_iteration_dwell`. Controller states migrate as in the table
   above; incompatible predictors are discarded rather than silently misread.
5. Resume writers and claim loops after readiness and compatibility checks.

feature PR. Coverage includes real optimizer updates and full-state continuation,
authentic v5/v6/v7 controller migration fixtures and state-invariant recovery,
legacy/modern/mixed learning-history precedence, focus-transfer event ordering in
a real Chromium browser, and shared analysis task/waiter bounds. Exact local

## Limitations

- The Champion controller's regularized uncertainty is a lightweight, conservative
  per-evaluation estimate, not a confidence interval for playing strength; the
  paired protocol is not modelled exactly. Measuring change from a single noisy
  baseline is inherently noisy, and a very different new Champion needs a few
  comparable observations before a change is allowed.
- Older unrecorded training settings cannot generally be reconstructed. Compact
  inference exports do not carry the full learning lineage; `last.pt` does.
- Learning benchmark timings exclude network/JSON parsing, the navigator/header
  and open tables; heap figures exclude native DOM/SVG/GPU memory and transient
  peaks. Full 100,000-point actions can still occupy the main thread for hundreds
  of milliseconds.
- Existing limits still apply to analytics: the search-time ceiling can stop MCTS
  before its simulation budget, model inference cancellation is cooperative, and
  Chromium mobile emulation is not physical-device validation.
- Browser coverage uses Chromium desktop/phone emulation rather than physical
  devices. CUDA/MPS validation and target-host deployment remain operator work.
  Existing dependency/test warnings and Vite's bundle-size advisory remain
  separate from passing functional checks.
